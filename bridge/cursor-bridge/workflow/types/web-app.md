## Add at project-end.delivery for web-deployment

- **Deploy the release** (a hosted web application): steps 1 to 5 in this order, each only after the one before it has succeeded, and step 6 when step 4 or step 5 fails, its own actions too each only after the one before it has succeeded:
  1. **The owner's yes**, first, since a deployment acts outside the repository and a revert does not undo it: the yes names the release, the pause step 2 makes and how long it may last (and the writes from outside it refuses, which a sender that does not retry loses), and the way back in step 6. The deployment procedure is recorded in `docs/INVENTORY.md` (Resources: the host, its platform and account, the command that deploys) before the first deployment; the supervisor runs it, or the owner through a run sheet where it needs a key the session does not hold.
  2. **The pause.** The product stops taking writes, neither its users' nor any from outside (a provider's notices, its scheduled jobs), in a maintenance or read-only mode in which it still answers at its address, and the pause is seen to hold: a marker write that changes no user's data (one the product discards, or one removed afterwards) is tried and refused. A product with neither mode cannot be checked while it takes no writes, so its design gives it one, a change like any other, before its first deployment. The pause lasts until step 5 passes, step 3 stops the deployment, or step 6 has brought the previous release back and its check has passed; where step 6 puts a question to the owner or tells them of a failure, until their word.
  3. **The backup, proved.** With writes held, the owner's live data is backed up, so the backup holds every write, to storage on the platform or of the owner's that Resources records with its platform and account, never into the repository or the Workspace, since it holds the users' data. The backup is then restored to a copy, kept away from the repository and the Workspace as the backup is, and read back, its contents compared with the live store's under the pause (the count of records in each table or collection, or a checksum of each), which proves this backup restores; where the release changes how stored data is kept, its migration is rehearsed on that copy and its result checked there. The copy is then deleted, since it holds the users' data; the backup stays where Resources records it. A backup that does not restore, or a rehearsal that fails, stops the deployment: writes resume on the unchanged live product, and the failure is a defect like any other.
  4. **The deployment.** The release's commit on `main` is deployed by the recorded procedure, which brings the release up in the mode of step 2, and its migration runs on the live data only here, as part of the deployment, never apart from a release (the design's migration policy, and founding rule N1's principle).
  5. **The check.** The deployed product is first seen to be still paused, since a deployment may restart it out of its mode: step 2's marker write is tried again and refused. It is then checked at its address with requests that change no user's data: it answers, and it reports the release's version where the design gives the version a place, the deployed commit read from the platform otherwise. When it passes, writes resume, and the report and the User Manual name the address and the version deployed.
  6. **The way back**, when step 4 or step 5 fails, a defect like any other, with writes held throughout. Where step 4 began a migration on the live data, the previous release may not run on that data, so the live data goes back to the backup of step 3, but only once the pause is seen to have held since the backup: step 2's marker write, tried again at the start of this step, is refused, as at every earlier try, and where the product records when each write from a user or from outside was made, none is later than the backup's time, the migration's own writes not counted. Then the backup is restored over the live data, and the restore discards no user's write. A marker write accepted at this try or an earlier one, or such a write later than the backup, means a user's write may have landed since the backup, and the restore is the owner's question. Where step 4 began no migration, the live data is left as it is. Only once the restore has succeeded, or where none was needed, is the previous release deployed by the same procedure, in the mode of step 2, and only once it passes the check of step 5 do writes resume. If the restore fails, or the previous release fails its check, writes stay held and the owner is told. Once step 5 has passed and writes have resumed, the backup is no longer a way back that loses nothing: restoring it later discards the writes made since, which is the owner's question.
