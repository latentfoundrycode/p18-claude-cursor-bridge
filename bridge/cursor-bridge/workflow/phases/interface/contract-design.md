## Contract design

The contract design is the interface phase's variant for a protocol other software calls, such as an MCP server's tools or a local API (`interface.md`, "The variants"). Its user is a program, so what the owner approves is what the part offers, in plain words; the contract's exact form is technical and is enforced by tests, not judged by the owner.

Write two things. **`docs/design/CONTRACT.md`**, in plain words: every operation the part offers, what it is for, what it needs, what it gives back, and each way it can fail, with one example call and reply per operation. **The contract file**, at the path `CONTRACT.md` names, in the protocol's own machine-readable form (a JSON Schema per operation, an OpenAPI document, an MCP tool list): each operation's name, its inputs with their types and which are required, its outputs, its errors with their codes, and the contract's version. State in `CONTRACT.md` how the version changes: what counts as a breaking change (an operation removed or renamed, an input made required, an output's meaning changed), and that a breaking change raises the major version and is a scope question for the owner.

The contract maps onto the agreed functionality **with no gaps, in both directions**, as a mockup does: every capability of `DESIGN.md` that other software reaches through the protocol has its operation, and every operation traces back to an agreed capability. Add every operation to `docs/REQUIREMENTS.md` as its own row (Source: contract operation "<operation>"), unless an existing row already covers it. The build plan then carries the increment whose tests check the built part against the contract file, so that the contract is enforced, never only described.

Where the part also has commands a person types (a service's administrative commands), those get the command design too (`interface/command-design.md`).

**Gate:** present `CONTRACT.md`'s operations, in plain words with their example calls, to the owner and get explicit approval of what the part offers before writing the build plan. Do not proceed on a contract with unaccounted gaps in either direction against the design. After approval a change that keeps every approved operation working as approved (an optional input, a clearer error) is recorded in `docs/CHANGES.md`; a breaking change escalates to the owner as a scope question.
