## Contract design

### What this variant is

The contract design is the interface phase's variant for a protocol other software calls, such as an MCP server's tools or a local API (`interface.md`, "The variants"). Its user is a program, so what the owner approves is what the part offers, in plain words; the contract's exact form is technical and is enforced by tests, not judged by the owner. Its artifacts are `docs/design/CONTRACT.md`, which states in plain words every operation the part offers, and the machine-readable contract file `CONTRACT.md` names, which tests enforce; the owner approves what the part offers, from `CONTRACT.md`, at the phase's gate (`interface.md`, "The gate").

### Writing the contract design

Write two things. **`docs/design/CONTRACT.md`**, in plain words: every operation the part offers, what it is for, what it needs, what it gives back, and each way it can fail, with one example call and reply per operation. **The contract file**, at the path `CONTRACT.md` names, in the protocol's own machine-readable form (a JSON Schema per operation, an OpenAPI document, an MCP tool list): each operation's name, its inputs with their types and which are required, its outputs, its errors with their codes, and the contract's version.

**Each operation says who may call it, and how the part tells.** Its entry in both files names the callers it accepts and the mechanism that tells them apart, never a claim the caller makes about itself. *Any local program* means the part listens on the loopback address only and, where it speaks HTTP, checks the Host and Origin headers and refuses a call from a web page, since every site the owner's browser opens can otherwise reach it. *A program holding the part's token* means a secret the caller presents and the part checks. *Only the part's own front end* means a secret the front end holds, never an Origin header or a client id. *Only the client that started it* means a server an MCP client starts over its standard input and output: it opens no listening socket, so its one caller is the process holding its pipes, and it needs no secret of its own to tell that caller apart. An operation that changes something or reads the owner's private data is open to any local program only if the owner approves exactly that at the gate. An operation open to every caller says so in those words.

**Each operation says what its inputs may reach:** the folder a path must stay inside, the records a caller may read or change, the hosts it may fetch from. For an MCP server this bound carries the most risk, because its caller is a model that a page or a document it read can steer.

**A refused call changes nothing and reveals nothing.** A call from a caller the entry does not accept, or one whose input reaches outside its bound, is refused with the error and the code the entry names. The refusal does not echo the credential presented, and it does not tell a thing that exists but is not the caller's apart from a thing that does not exist. The increment that enforces the contract then tests the refusals as well as the shapes of the replies: a call without the secret and one with a wrong secret, a call reaching outside its bound and, where the part speaks HTTP, a call from a web page's origin and one with a wrong Host header.

**Credentials.** A credential an operation needs travels as the protocol carries one (a header, the MCP authorization of the HTTP transport), never as an ordinary input and never in a URL's query string, and the example calls show it only as a plain placeholder, `<token>`, never as a string shaped like a real key. The part's own keys for the services it calls, and the tokens it issues to its callers, live where founding rule N2 puts a secret: a key file outside the Workspace, the product's encrypted store or the system's credential store, never an environment variable the owner sets (KP-032). A server an MCP client starts therefore reads the key file the client's configuration names, and the configuration never holds the key.

State in `CONTRACT.md` how the version changes: what counts as a breaking change (an operation removed or renamed, an input made required or its type narrowed, an output's meaning changed, an error's code changed, a caller refused that was accepted), and that a breaking change raises the major version and escalates to the owner as a scope question.

The contract maps onto the agreed functionality **with no gaps, in both directions**, as a mockup does: every capability of `DESIGN.md` that other software reaches through the protocol has its operation, and every operation traces back to an agreed capability. Add every operation to `docs/REQUIREMENTS.md` as its own row (Source: contract operation "<operation>"), unless an existing row already covers it. The build plan then carries the increment whose tests check the built part against the contract file (`planning.md`, "What the interface phase hands to the plan"), so that the contract is enforced, never only described.

Where the part also has commands a person types (a service's administrative commands), those get the command design too (`interface/command-design.md`).

### Approving the contract design

**Gate:** present `CONTRACT.md`'s operations, in plain words with their example calls, who may make each and what each may reach, to the owner and get explicit approval of what the part offers before writing the build plan. Do not proceed on a contract with unaccounted gaps in either direction against the design.

**After approval,** a change that keeps every approved operation working as approved, **adds none and widens none** (an optional input, a clearer error message) is recorded in `docs/CHANGES.md`. A breaking change escalates to the owner as a scope question, and so do an added operation and a widened one: a caller accepted that the approved entry refuses, or an input allowed to reach beyond its approved bound. Each of these makes the part offer something the owner has not approved, whether or not anything that was approved stops working.
