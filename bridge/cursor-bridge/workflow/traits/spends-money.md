# Spends money

## Add at intake.questions

For a part whose actions cost real money (a paid API, a purchase, a metered model or service), ask before design, and write each answer to the intake notes: which actions cost money, on which **platform and account** each is charged; the **worst case** of each, the most one run of it can cost when it goes wrong as well as when it goes right (every retry, every item of the largest input, a run that does not stop), estimated in that platform's own units and in money; and the **cap** the owner sets, the most the project may spend in all, per month or per run as the owner names it, with what happens at the cap (the action stops and the owner is asked; never a silent overrun). The loop's own paid actions (a contract capture, a paid run of an increment, a re-recording, a benchmark against a paid service) are tracked against the cap by the supervisor; where the product itself spends in the owner's use, the design states how the product enforces the cap, and the cap is a value the owner chose, fixed in a test (rule 52). This trait adds no design section, so the intake notes carry its three duties to the design as requirements of it: how the product enforces the cap, where it spends in the owner's use; the folder that holds the store of paid results (its addition at `configuration.items`); and how a speed budget that includes a paid service's time is measured (its addition at `delegation-loop.brief-constraints`). No paid action of the loop runs without the owner's approval first, given in words for that action, with its estimate against the worst case and the platform and account named in the same sentence; an approval covers the action it names, never the next one, and the escalation the trait *external services* asks once per service (its addition at `planning.stages`) settles the service's key and account only: where a part has both traits, the contract capture's live call that escalation names is, when it costs money, a paid action of the loop like any other, approved for itself as this trait asks, and so is every later capture or re-recording of that service. A paid call is a remote call, whose wait the trait *external services* bounds (its addition at `delegation-loop.inspect-checks`), so a part that pays a remote service is classified with *external services* too, which the design gate's trait decision checks.

## Add at configuration.items

**The store of paid results.** Before the first paid action, configure where its results are kept: a folder the design names, outside the repository and the Workspace, which no clean, reset, cache purge or test teardown reaches, each result kept with the request that bought it, the request's key left out, so that a retry, a rerun or a crash reads the result already paid for instead of buying it again. A contract capture, a re-recording or a live smoke the owner approved buys its replies afresh: it reads only the replies it has bought itself, each written there with the run that bought it in place of the one recorded before, so that a resumed run never takes an older reply for a new one. The dry run, a benchmark and a test run keep their results in a store of their own instead, outside the repository, the Workspace and this folder, empty when each run, and each repetition of a benchmark, starts, deleted whichever way it ends, and never reading this store, so that no stand-in's reply reaches it and a benchmark counts every paid call a run from cold makes. Every other run reads this store before it buys. The store is a Resources row of `docs/INVENTORY.md`, named by its role and never by a path of this computer (rule 54). **The cap** is recorded where the owner can read it: a Decisions row `Spending cap: <amount> <per month or per run> on <platform and account> (<the owner's words>, <date>)`, beside the provider's own spending limit in the account's Resources row, which configuration's spending-limits item sets.

## Add at delegation-loop.brief-constraints

The builder runs no paid action: a brief that needs one says so, and the paid run is the supervisor's, after the owner's approval for it. Every paid call the part's code makes goes through the store of paid results as its configuration says: its result written there with the request that bought it, and the store read before a call is bought, so a retry never buys twice, a capture, a re-recording, a live smoke, the dry run, a benchmark and a test run keeping the rule that configuration gives them, and no request kept there with its key. Before any paid run, the brief's increment has run once **dry**: on the development data the inventory's `Development data:` decision names (rule 55; a copy of live data only with the owner's yes for that run, kept away from the repository and the Workspace, since it holds the users' data, and deleted whichever way the run ends), with a stand-in provider that answers as the real one does (its recorded replies, the trait *external services*' contract capture) and charges nothing, the run's every paid call counted and compared with the estimate. The first paid run of a contract capture, which has no recorded replies to stand in yet, and a paid action with no remote service behind it (a purchase) run instead at the smallest size that answers them, under their own approval, their paid calls counted beforehand against the estimate. A benchmark of an operation that calls a paid service runs against the dry run's stand-in provider, which measures the operation's paid calls for a cost budget and the part's own time, never the service's: a speed budget that includes the service's time is one the floor cannot check on the stand-in, so the design that names one says how it is measured, any paid run the measuring needs approved as a paid action of its own and run by the supervisor, and until the design says so the floor reports the budget `NOT MEASURED`, a block, never a pass, since no benchmark of it runs on the stand-in. A speed budget of an operation that calls a paid service includes the service's time unless the design records, in the owner's words, that it leaves that time out. The part's own time on the stand-in is always reported under a benchmark name of its own, never under the benchmark and metric a budget that includes the service's time names. A benchmark run against the paid service itself is a paid action of its own, approved as one, never part of the benchmark floor or of CI.

## Add at delegation-loop.inspect-checks

No paid action ran unapproved, and none bypassed the store: the supervisor reads the run's log and the store of paid results, and the provider's usage for the run's time where a Resources row records a way to read it (otherwise the owner reads it at the stage close, by a run sheet); a paid call with no approval naming it, a paid call in the diff that does not both read the store first and write its result there (a capture, re-recording or live smoke reading only the replies its own run bought, in an approved run of it only, as the store's configuration says), a capture, re-recording or live smoke that reads a reply its own run did not buy, a run other than those the configuration names that skips the store, a stand-in's reply written to the store of paid results, a dry run, benchmark or test run that reads it, a store of paid results inside the repository or the Workspace or a request kept there with its key, a dry run's, benchmark's or test run's own store left after its run, or a stand-in result reported under the benchmark and metric a budget that includes a paid service's time names (the benchmark results read against the budgets file and the design's record, in the owner's words, of the speed budgets that leave that time out, any other speed budget of an operation that calls a paid service read as including it), is a blocking finding, a paid call that ran unapproved also recorded as an issue and told to the owner in the next report's first line with its amount, platform and account.
