# AI models

## Add at intake.questions

For a part whose results come from models, ask before design, and write each answer to the intake notes: which results a model produces; for each, the **evaluation set** that stands in for exact tests (the inputs, drawn from the owner's real cases, and what a good result is for each, as the owner judges it), and the **threshold** a result must meet (a share of the set passing, a score, a rate of a named failure no higher than a figure), each threshold the owner's value, fixed in a test (rule 52).

## Add at design.sections

The design has an **Evaluation** section: each evaluation set, where it lives and how it grows, the judge of each result (a rule a program checks, or a model of another family than the one judged, rule 51), and each threshold with its source, a result below it blocking the change at the test step.

## Add at configuration.items

Each model is **pinned**, a model judge included: its exact identifier and version, never a name that moves to a newer model, recorded in `docs/INVENTORY.md` (Resources), and changed only as a change of its own whose evaluation runs before and after. **Recorded outputs** have a home: the model's replies to the evaluation set, kept with the model's identifier and the date, under the project's test fixtures, and beside them a model judge's verdicts on them, judged again whenever the outputs are recorded again or anything that shapes the judged result from them changes (the code after the model's reply included), so that, while nothing that shapes the judged result changes, the evaluation runs again without calling any model; each verdict is kept with the judged result it read, so that a change to that result shows by comparison. The evaluation set's inputs and the recorded outputs are scrubbed as a contract capture's fixtures are (no key, no secret, nothing about a person the owner has not agreed to commit), and the owner, who chooses the cases, is asked before the first is recorded whether they may be committed; a case that cannot be scrubbed, or that the owner keeps out, is kept with its outputs, and the verdicts and judged results recorded beside them, outside the repository, in a development-only place the Evaluation section names by its role, never by a path of a computer (rule 54), apart from the live data and never read by the product (rule 55), and a run without it (CI) reports that case as not run, never as passed.

## Add at delegation-loop.test-checks

The evaluation runs against its thresholds on the recorded outputs and their recorded verdicts with the change's tests: a result below a threshold is a correctness-class block (step 7), and an exact-match assertion on a model's output, where the evaluation set should judge it, is a finding of its own. The evaluation at this step runs the whole set, the cases kept outside the repository read from their place: a case not run here is a correctness-class block too, as `NOT MEASURED` is at the benchmark floor, and the not-run report of a run without those cases (CI) is that run's alone. A change that alters the prompt, the model or its settings records new outputs first, and new verdicts on them; a change to the code that shapes the judged result from a recorded reply has that result judged again; each in a run the owner has approved where a model costs money, and the evaluation reads those. Until they are recorded, the evaluation does not pass on the verdicts recorded before the change: a change whose judged result changed and whose new verdicts are not yet recorded is blocked at the test step, however the old verdicts read. A judged result has changed where it differs from the one kept beside its verdict; where a model costs money, the block waits on the run the owner approved, which the supervisor starts (a builder runs no paid action), never on a re-delegation.
