# TASK-051: records-migrate.py, the migration program

## Objective
Release B2 gives the records that both the model and a program read a YAML front-matter header holding the values; the prose stays, and each record's checker compares the two. TASK-046 to TASK-050 (merged) built the header reader, the schemas, the agreement helper and one fallback reader per record kind in `bridge/cursor-bridge/bridge_env.py`, and made every program read the header first. Today no record has a header, and nothing writes one. This increment adds the program that does: `bridge/cursor-bridge/records-migrate.py`. Given a project root (or record paths), it finds the eight kinds' records, and for each record with no header it writes one composed from `bridge_env`'s own fallback reading of the record's prose, so the header agrees with the prose by construction. Each write is atomic and checked before the move. With `--check` it writes nothing and lists what it would do. It lists, and leaves alone, what it cannot read or cannot write. The supervisor, the calibration and the stage's demonstration will run one command, `python ~/.claude/cursor-bridge/records-migrate.py --check`, from a project's Workspace root. This increment also adds the program's permission rule, its command-reference entry and the thirteenth `dump-cli.py` load in its test. It writes no header into any record of this repository (that is TASK-054, by the installed program).

Satisfies: R-062 - Migration is a program: `records-migrate.py` enumerates the eight kinds' records from a project root or from given paths and writes each header-less record's header from `bridge_env`'s fallback reading of its prose, atomically and read back before the move, marks `historic` from the one merged set, leaves a headed record unchanged, refuses a malformed one, lists what it cannot read or write, and with `--check` writes nothing. (Full text: the requirement's row in `docs/REQUIREMENTS.md`. Its template and calibration half is TASK-052's, not yours.)

1. **R1. The program's shape.** `bridge/cursor-bridge/records-migrate.py`, ASCII program text, the shebang, a module docstring whose usage line is `python records-migrate.py [--check] [--base <ref>] [<project root>|<record>...]`. A top-level `build_parser()` taking no argument returns an `argparse.ArgumentParser` with `--check` (a flag), `--base` (default `origin/main`) and the positional paths (zero or more). A top-level `main(argv)` takes the arguments without the program's name and returns the exit code as an int; the `__main__` block calls it with `sys.argv[1:]` and exits with its result. Importing the module runs nothing but its imports. Its one bridge import is `bridge_env`, as plan-check.py imports it. No `yaml`, no third-party import, no new dependency.
2. **R2. Arguments.** Nothing given: the current folder is the root. One folder given: that folder is the root. A second folder: exit 2, nothing written. A folder and record paths together: exit 2, one usage line saying to give a project root or record paths, not both, nothing written (ruling 7). Record paths alone: those records only, in the order given, the current folder as the root (for the merged set). A `--base` beginning with `-`, in any form (`--base -x`, `--base=-x`, `--base=--all`): exit 2 before any record is read, nothing written.
3. **R3. The kind rule and the enumeration.** From a root, the program enumerates, in this order, files of one kind sorted by name: `docs/PROJECT_STATUS.md` (`project-status`); every `docs/BUILD_PLAN*.md` (`build-plan`); every `handoff/*.md` directly in `handoff/` whose name `HANDOFF_REPORT_NAME` does not match (a report, `<ID>-report.md` or `<ID>-r<N>-report.md`) and `HANDOFF_RESOLUTION` does not match (a resolution file) (`brief`); `docs/INVENTORY.md` (`inventory`); `docs/REQUIREMENTS.md` (`requirements`); `docs/diagrams/INDEX.md` (`diagram-index`); `docs/diagrams/DEVIATIONS.md` (`deviations`); `docs/RUN_PARAMETERS.md` (`run-parameters`). A report, a resolution file or any other file is never listed and never written. A given path is told its kind from its name by the same rule. A given path under no kind, a report or a resolution file among them (ruling 6), is listed `cannot read <path>: not a record kind` and the run goes on; it changes no exit.
4. **R4. The path shown.** Relative to the project root, with forward slashes, for an enumerated record; exactly as given, for a given record path (ruling 2).
5. **R5. A record that has a header.** A record whose first line is `---` has a header. Where `read_header` raises `HeaderError`, or `check_header(kind, header)` returns a finding, the program prints `HEADER MALFORMED: <path>: <the HeaderError's message, or the findings>`, exits 2, and stops at that record: the records before it written and listed, the records after it neither written nor listed, the malformed record unchanged (ruling 10). This holds with and without `--check`. Otherwise it prints `has a header <path>` and leaves the record byte-identical. It never compares a well-formed header with its prose: a header that disagrees is the record's checker's finding, not the migration's (ruling 8).
6. **R6. The header composed from the fallback.** For a record with no header, the header holds `record: <kind>`, `header: 1` and every other key of `HEADER_SCHEMAS[kind]`, each mapping's keys in its schema's order at every depth, each value taken from the kind's fallback over the record's decoded text (`decode_record_bytes`) so that `header_agrees` finds nothing:
   - `project-status`: the six values of `status_fallback`.
   - `build-plan`: one stage per stage of `plan_prose_fallback(text, merged)`, `demonstration` true where the stage has a `Demonstration:` line; each increment's eleven keys as `_plan_agrees` reads the prose (`kind` `increment` where no `Kind:` line stands; `parallel` from `yes`/`no`, `false` where absent; `parent` and `deferred` `null` where absent; an absent list line, or the filler `none` on `Parent:`, `Depends on:` or `Diagrams:`, the empty list), and `historic` by R8.
   - `brief`: `id` and `round` from `parse_review_name(<file name without .md>)`, `round` an integer (1 for a plain name); `satisfies`, `scope`, `merge_unit` and `blocking_class` from `brief_prose_fallback`. `satisfies` is the fallback's list exactly, order and repeats kept (ruling 9). A file name `parse_review_name` refuses is listed `cannot read <path>: <reason>`, nothing written.
   - `inventory`: `reflected_through` and `development_data` from `inventory_fallback`; `tables` with all four sections, each its header row as `columns` and its first column as `key`.
   - `requirements`: `columns` the table's header row; `roles` `id`, `status` and `evidence` the header row's 1st, 4th and 5th cells; `statuses` `[planned, built, deferred, dropped]`.
   - `diagram-index`: `columns` the header row; `roles`, the i-th role of `DiagramIndexRoles` (`id`, `level`, `kind`, `status`, `file`, `refines`, `realizes`, `enforced_by`, `why`) the header row's i-th cell.
   - `deviations`: `columns` the header row; `roles`, the i-th role of `DeviationsRoles` (`diagram`, `from`, `to`, `as_built`, `since`, `resolved_by`) the header row's i-th cell.
   - `run-parameters`: the nine values of `run_parameters_fallback`.
   - A tabular record whose fallback gives no header row, a missing inventory section, or fewer header cells than its roles need, is listed `cannot read <path>: <reason>`, nothing written, the run going on.
7. **R7. The subset's form.** The header is written as `read_header` reads it and as `yaml.safe_load` reads it to the same value (DESIGN.md, "The reader"): `key: value` lines, nesting by two spaces; an integer as a decimal; `true`/`false`; `null` for a null; a string plain only where the subset reads it plain (a word of letters, digits, `_`, `-` and `.` starting with a letter and not, in any case, one of `yes`, `no`, `on`, `off`, `y`, `n`, `true`, `false`, `null`, `~`), and double-quoted otherwise: a date, a version starting with a digit, a typed word (`on`, `off`), a value holding a space, a colon, a slash or `#`, a non-ASCII character; inside quotes only the escapes `\"` and `\\`; the empty string as `""`; a list in flow form (`[a, b]`, `[]` when empty) where every item is a short scalar and in block form otherwise; every list of mappings in block form (the subset refuses a flow mapping). The opening and closing `---` lines frame the block. The header's lines end as the file's lines do (CRLF where the file uses CRLF, LF otherwise), and the original bytes follow the closing `---` line unchanged, byte for byte.
8. **R8. `historic` and the merged set.** A plan increment the fallback reads with neither a `Scope:` nor a `Kind:` line is `historic: true` where its ID is in the merged set, and `historic: false` otherwise, as is every other increment. The merged set is `bridge_env.squash_merged_ids(<root>, PLAN_ID_PATTERN, ref=<--base>)`, read lazily: only for a plan file holding such an increment, and at most once per run. Where it returns `None`, that plan file is listed `cannot read <path>: merged set unreadable (<reason>)` (the reason your words, naming the ref, since the function gives none), left untouched, the run going on. A historic increment's `kind` is `increment` and `parallel` `false`, and its lists are written as the fallback reads them: `[]` for an increment with no field lines, and the prose's list where a `Satisfies:` or `Depends on:` line still stands, never `[]` in its place (ruling 4). The read-back passes the merged set to `plan_prose_fallback(text, merged)`. Before any of this, a plan file in which any increment's raw `Scope:` value (from `walk_plan_prose_body(plan_body(text))`) makes `plan_scope_paren_unbalanced` true is listed `cannot read <path>: unbalanced parenthesis in <id>'s Scope` (the first such increment), nothing written.
9. **R9. A brief's Scope refusal.** The program calls `bridge_env.parse_scope` on the brief's text; where its second value (the refusal) is not `None` (an ellipsis, an empty Scope), it prints `cannot read <path>: <that refusal value>` and writes nothing, even though `brief_prose_fallback` alone would give `scope: []` (ruling 5). A merged brief among these is never repaired and stays header-less. Unread pieces (the third value) beside readable paths are not a refusal: such a brief is written, its `scope` the paths read.
10. **R10. A read-back that finds anything, or an `OSError` while writing, reading back or replacing, prints one line naming the path and what failed (your wording, beginning with none of `would write `, `has a header `, `cannot read `, `cannot write `), removes the temporary file, leaves the record byte-identical, and exits 3, the run stopping there. No temporary file is left behind on any outcome the process survives. Killed between the temporary file's write and the replace, the record is whole.
11. **R11. The status file's older cap.** Before writing a status file, the program counts the whole new file's text (header and body) as the older inventory-check counted it (Context): over 12,000 characters, it prints `cannot write <path>: <n> characters with the header, over the older cap; trim the body first`; else over 120 lines, `cannot write <path>: <n> lines with the header, over the older cap; trim the body first` (ruling 3). One line per record; nothing written; the run goes on.
