# TASK-061: A review run's own launcher rows (R-079)

## Objective
`bridge/cursor-bridge/bridge-run.py` (the launcher) appends one row per run to the launch folder's `run/launcher/runs.jsonl`, and `learned_limit` sets a kind's `--limit auto` from the longest healthy row of that kind. A Review B run starts suites of its own (in its scratch folder or the checkout), and their rows teach the launcher a limit no build needed; nothing tells the supervisor that the review ran them. Separately, the bridge's own launcher tests start the launcher with the checkout as the working folder in several places, so their rows (one with `--limit 3`) land in the checkout's real log. This increment makes `learned_limit` ignore every row whose start lies inside a `review` row's run, read from the log's own times; makes `review-guard.py verify` print, after its verdict and never changing it or the exit code, one note naming the launcher rows written during the review's own run; and makes every launcher test that starts the launcher do so in a temporary folder of its own. The supervisor's acceptance tests are written and committed; your work is to make them pass without breaking the existing ones.

Satisfies: R-079 - A review run's own launcher rows neither teach the limit nor go unseen (C8, J2): `learned_limit` ignores every row whose start lies inside a `review` row's run, read from the log; `review-guard.py verify` names, as a note and never a flag, the launcher rows written during the review's run by id and kind, the review's own row apart; the bridge's own launcher tests write their rows under a temporary folder, never into the checkout's `run/launcher/`.

## Requirements
1. **A row's start.** A row's start is read from its `id`: the whole id is `YYYY-MM-DDTHH:MM:SSZ` optionally followed by `-<digits>`, parsed as a UTC time with the language's date parser (never by slicing). A row whose id has any other form has no start: it is never ignored by Requirement 2 and never named by Requirement 4.
2. **`learned_limit` ignores a review's own rows (C8).** `learned_limit(kind, folder)` ignores, for every kind, every row whose start lies inside a review row's run: from the review row's start to its start plus its `seconds`, both ends included, at whole-second resolution. A review row is a row with `kind` `review`, a start, and `seconds` an `int` or `float` that is not a `bool` and is not below 0; any other review row has no end and ignores nothing. A review row is never ignored on account of its own run (the `review` kind keeps learning from its own rows). Rows outside every review run are taken as today; the `healthy`, `seconds`, `exit` and cap rules are unchanged. The log is read once per call, through `bridge_env.read_runs_jsonl` as today.
3. **One reading.** The start and run of Requirements 1 and 2 are computed by one piece of code, read by `bridge-run.py` and by `review-guard.py` (in `bridge_env.py` or wherever your design puts it within Scope), so that the launcher and the guard cannot disagree on which rows lie inside a review.
4. **`verify`'s note (C8).** On the success path, after the `review-guard: OK ...` line, `verify` prints to stdout exactly one line naming, by id and kind, every row of `<root>/run/launcher/runs.jsonl` whose start lies inside the review's own run, in the log's order. The review's own row is the review row whose id is the launch time `launch_info` returns followed by `Z` (with or without a `-<digits>` suffix); that row itself is not named. Where no such row exists, where the review row has no end (Requirement 2), where the `.err` file or its launch line is missing, where the log is missing or unreadable, or where no row lies inside, nothing is printed after the OK line. The note never changes the verdict, the mark, or the exit code; it does not begin with `review-guard: OK` and holds no `GATE-INTEGRITY`. It prints a row's id and kind and no other field; a kind that is not a plain word of ASCII letters is not printed as it stands (your choice how; state it). Where more than one review row matches the launch time, your choice which (state it). Whether a note also prints on a GATE-INTEGRITY or CANNOT VERIFY path is your choice; if it does, it comes after that verdict and changes nothing; state what you chose.
5. **The launcher tests write no row into the checkout (J2).** Every test in `tests/test_bridge_run.py`, `tests/test_bridge_run_slot.py`, `tests/test_bridge_run_driver.py` and `tests/test_release_s_launcher.py` that starts the launcher (as a subprocess or in process through `main`) does so with its working folder a temporary folder of its own under `tmp_path` (or another per-test temporary folder), by the test's own arrangement (`cwd=`, `monkeypatch.chdir`), never by a launcher option or an environment variable. A test that needs a log creates `run/` in its own folder, as `test_every_run_is_logged_without_its_prompt_and_can_be_marked_healthy` does. Each test keeps what it asserts; where a test needs the checkout's files (a path relative to the Workspace), it names them by absolute path.
6. **Your own cases.** Add cases naming R-079 (in a name, docstring or comment): in `tests/test_bridge_run.py`, `learned_limit` with a review row's boundary (a row starting exactly at the review's end, and one exactly at its start with a suffix), a review row whose `seconds` is a string, a bool, or negative (ignoring nothing), a row whose id is not the launcher's form (taught as today, never an exception), and the `review` kind still learning from its own rows; in `tests/test_review_guard.py`, `verify` with a log holding a malformed line and a row whose id is not the launcher's form (no exception, exit and verdict as without them), and with a missing `.err` file (no note, exit unchanged).
