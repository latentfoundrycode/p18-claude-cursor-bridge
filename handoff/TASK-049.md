# TASK-049: The tabular records' headers

## Objective
Release B2 gives the records that both the model and a program read a YAML front-matter header. TASK-046 (merged, PR #137) built the header reader, the schemas and the agreement helper in `bridge/cursor-bridge/bridge_env.py`; TASK-047 (PR #138) made the status file's six readers read its header first; TASK-048 (PR #139) did the same for the plan and the briefs. This increment does it for the four tabular records: `docs/INVENTORY.md` (`record: inventory`), `docs/REQUIREMENTS.md` (`record: requirements`), `docs/diagrams/INDEX.md` (`record: diagram-index`) and `docs/diagrams/DEVIATIONS.md` (`record: deviations`). A tabular header declares the table's shape (sections, columns in order, role or key columns), never its rows. Today no program reads a header on these four files: a header block at a file's top is ignored. After this increment every program that reads one of them reads the header first through `bridge_env`, splits each row by the declared columns and reads it by role, and each table's one owning checker compares the declared shape with the table and prints `HEADER DISAGREES: <key>`. Where a file has no header, the program falls back to one prose reading per record, moved into `bridge_env` from the program that owns it today, unchanged in rule. Three retired second readings disappear: (7) `conformance-check.py`'s heading-word guess of the inventory's sections, (8) `plan-check.py`'s column-position read of the index, and (9) `diagram-check.py`'s whole-text `R_RX` over the register. The aim is that each table has one reader, one owner and one shape, so two programs can never read the same row two ways.

Satisfies: R-060 - The tabular records' headers declare the table's shape, never its rows: `docs/INVENTORY.md` carries `record: inventory` with `reflected_through`, `development_data` and `tables` (the four sections, each its `columns` and `key`), read first by `inventory-check.py` and `conformance-check.py`; `docs/REQUIREMENTS.md` carries `record: requirements` with `columns`, `roles` (`id`, `status`, `evidence`) and `statuses` (the allowed set, exactly the four words `planned`, `built`, `deferred`, `dropped` in this release, a list of fewer or other words malformed, a Status cell opening with a word outside them the register check's finding as today), read first by `completion-check.py`, its owning checker, and `diagram-check.py` (the R-ids traced read from the id column, its whole-text `R_RX` over the file retired); `docs/diagrams/INDEX.md` carries `record: diagram-index` with `columns` and `roles` (every column), read first by `diagram-check.py`, its owning checker, and `plan-check.py` (its column-position read retired); `docs/diagrams/DEVIATIONS.md` carries `record: deviations` with `columns` and `roles` (`diagram`, `from`, `to`, `as_built`, `since`, `resolved_by`), read first by `diagram-check.py`, its owning checker; `development_data` is the first cell of the Decisions row that begins `Development data:`, the one value a tabular header copies from its table; each program splits a row by the declared columns; each table's owning checker (`inventory-check.py` the inventory's) compares the declared columns with the table's own header row (`HEADER DISAGREES: columns`, a role's column absent from the header row `HEADER DISAGREES: roles.<role>`, each a finding, exit 1; a role naming a column absent from the header's own `columns` malformed) and the declared sections with the file's headings (`HEADER DISAGREES: tables.<section>`), `inventory-check.py` comparing `reflected_through` with the `Reflected through:` line and `development_data` with its row too, and fails a difference, the other reader trusting that check; each keeps the one fallback `bridge_env` holds for a file with no header (`conformance-check.py`'s heading-word guess of the inventory's sections retired), tested on a header-less record, and refuses a malformed header as R-058 says.

## Requirements
1. **The tabular fallback readers move into `bridge_env.py`, one copy each.** The inventory reading (the sections and their header rows and rows, `reflected_through`, `development_data`), the register reading (`parse_register`, with the header row also in its original case), the index reading (first table, its header check) and the deviations reading, each as the Context describes it, unchanged in rule. 2. **Header first, in every program, for every record it reads.** A record whose first line is `---` is read through `read_header` and `check_header(<kind>, header)`. A header either refuses prints `HEADER MALFORMED: <path>:<line> <what>` and the program exits 2, never falling back. A well-formed header's declared `columns` split the rows and its `roles` (or, for the inventory, its `tables`) name the columns each program reads, from the file's body. A file with no header is read through the fallback of Requirement 1 and gives exactly today's answer.
3. **`inventory-check.py`, the inventory's owner.** It compares a well-formed header with the fallback through `header_agrees("inventory", header, fallback)` and prints each token as `HEADER DISAGREES: <token>`, a failure counted with the others before the `RESULT:` line, exit 1. It keeps the status-file reading TASK-047 gave it unchanged.

5. **`completion-check.py`, the register's owner.** It compares a well-formed header through `header_agrees("requirements", header, fallback)` and prints each token as `HEADER DISAGREES: <token>`, a failure, exit 1.
