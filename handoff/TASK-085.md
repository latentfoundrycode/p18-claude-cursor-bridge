# TASK-085: The mutation engine on an editable install (R-106)

## Objective
`bridge/cursor-bridge/mutation-run.py` (run as `python ~/.claude/cursor-bridge/mutation-run.py run/supervisor/<id>-mutants.json`) copies the Workspace's tracked files to a scratch folder, puts only the copy's root on the run's `PYTHONPATH`, and proves with a pytest collection (the "resolution check") that every module the mutants touch resolves inside the copy and that no module is loaded from the Workspace. A project installed into its environment in editable form puts a Workspace folder on the interpreter's import path (a path entry), or answers through a finder that leaves no entry; either way its package is imported from the Workspace, and every run is refused with exit 2 by a line that names neither the cause nor a remedy. This increment makes the program read the import path of the interpreter it is about to use, map every Workspace entry to the same folder of the copy and put those folders ahead of the copy's root; lets a mutants file name such roots itself under a new key, `import_roots`, refused where unsafe; hands the same roots to the reading of a mutant's dotted module name, so a module under `sdk/src/pkg/` is checked as `pkg.<module>`; and makes the resolution check's refusal, where a module is still loaded from the Workspace, name the module, the place, the usual cause and the key. The resolution check stays the proof, with exit 2. The supervisor's acceptance tests are written and committed; your work is to make them pass without breaking the existing ones.

Satisfies: R-106 - The mutation engine runs on a project installed into its environment in editable form (C27). Its row in `docs/REQUIREMENTS.md` (line 134) reads: "before its checks `mutation-run.py` reads the import path of the interpreter it is about to use, in the run's environment with the copy as working folder, maps every entry that resolves inside the Workspace to the same folder of the copy and puts those folders first on the run's `PYTHONPATH`, ahead of the copy's root; the same roots serve the reading of a mutant's dotted module name; a mutants file may name such roots itself under `import_roots`, each relative to the Workspace root and refused where it is absolute, leaves the Workspace or passes through a link; the resolution check stays the proof with exit 2, and where it fails its line names the module, the place it was loaded from, an editable install as the usual cause and the `import_roots` key."

## Requirements
1. **R1. The interpreter probe.** In both modes, after the copy is built and before the first resolution check, the program starts `sys.executable` once per run (not once per resolution-check call), through `run_process`, with the copy (`copy_root`) as working folder, in the environment a resolution check of that copy gets (the `pytest_env` environment), under `timeout_sec`, and reads the interpreter's import path (`sys.path`) from what it prints. Any failure (the interpreter cannot be started, a timeout, a non-zero exit, output that does not parse, an entry that is not a string) leaves the run going on with the copy's root alone, as today, never an exit of its own and never a traceback. The probe imports no module of the project and no module from the copy.
2. **R2. Which entries are mapped.** Each probe entry that resolves inside the Workspace (the Workspace root itself included), compared after the same resolution of both paths and without regard to letter case on Windows (`os.path.normcase`), is mapped to the same Workspace-relative folder of the copy. Entries outside the Workspace are left as they are: neither mapped nor added to `PYTHONPATH`. A mapped folder is checked to lie inside the copy before it is used.
3. **R3. The run's path.** Every pytest run of the run (the resolution check, the baselines, each mutant's run, each `--checkpoint` item) gets on `PYTHONPATH` the mapped folders and the `import_roots` folders (R4), each joined to the tree that run works in (`copy_root`, or `base_root` for the baselines), standing ahead of that tree's root, the plugin folder staying where it stands today. A folder the tree does not hold may be left out. Their order: the `import_roots` folders first, in the file's order, then the mapped folders in the order the probe printed them, then the tree's root.
4. **R4. The `import_roots` key.** The mutants file accepts a top-level `import_roots`: a list of strings, each a folder relative to the Workspace root, `/` or `\` as separator (normalized as the file's other paths are). An empty list is allowed and adds nothing. It is checked before any copy or process is made, and refused with exit 2 (a `Refuse`, so the line goes through `run_main`) for every one of these forms, each line naming the key `import_roots`:
   - not a list (a string, a number, an object, and `null` given explicitly, which is refused, never read as absent): the line says it must be a list of strings, and never says `unknown field`;
   - an entry that is not a string (a number, a list, an object, `null`): the same;
   - an entry that is absolute in any form the platform knows (a leading `/` or `\`, a drive letter with or without a separator after it, a UNC `\\server\share` path, the `\\?\` and `\\.\` forms): the line holds the word `absolute`;
   - an entry that leaves the Workspace by any `..` form (`..`, `../elsewhere`, `sdk/../..`, a `..` after a backslash): the line holds `leaves` or `outside`. An entry holding a `..` component that stays inside the Workspace is refused too, as every other path of the file is;
   - an entry that `path_bad` refuses for another reason (empty, a `.` or empty component, a first component `.git` in any case, a component ending in a dot or a space or holding a colon): refused, as the file's other paths are;
   - an entry any component of which, from the Workspace root down to the folder it names, is a symbolic link or a junction (any reparse point, `bridge_env.is_link`), the walk failing closed where a component cannot be read: the line holds `link`.
   In the ordinary mode an entry naming a folder the working tree does not hold, or naming a file, is refused with exit 2 by a line naming the key and the entry, so that a mistyped root is told and never silently ignored; in the `--checkpoint` mode such an entry is judged at the commit as R9 says. `import_roots` is never an unknown field any more; every other unknown top-level key keeps its `unknown field` refusal.
5. **R5. The same roots for the dotted name.** `dotted_module_paths`, the generated plugin's `_dotted` and `module_file_at_commit` each read a Workspace-relative file under every root of the run: the Workspace root and `src/` as today, plus each mapped folder of R2 and each `import_roots` entry, as Workspace-relative prefixes. So `sdk/src/pkg/calc.py` with root `sdk/src` is checked as `pkg.calc` (beside `sdk.src.pkg.calc` from the Workspace root). The roots enter the generated plugin as data, a `json.dumps` or `%r` literal as `MUTATED` and `TRACKED` do, never as code. The resolution check's refusals of a mutated module apply to every name so formed.
6. **R6. The cache key.** `import_roots`, as the file gives it after normalization, is part of each mutant's cache key, so a kept kill is served while it is unchanged and the mutant runs again once it changes. The probe's mapped roots, as Workspace-relative folders in the order R3 uses, join the key too, so a change of the environment's editable install reruns a kept kill (more reruns, never fewer). The cache file's format and the rest of the key are unchanged.
7. **R7. The refusal line for a module loaded from the Workspace.** Where the resolution check still finds a module loaded from the Workspace, the run is refused with exit 2 by a line that names the module (its name in `sys.modules`), the place it was loaded from (its Workspace-relative path), that an editable install of the project is the usual cause, and the `import_roots` key as the remedy where the install answers through a finder. The program's source keeps the format text `module from Workspace path %s was loaded` within that line (Context: `tests/test_loop_text_windowless.py`). Nothing is cached for a refused run. The line stays ASCII and stays one line.
8. **R8. The path entry itself is no module.** The resolution check no longer reports a Workspace entry on the import path as if it were a module: the line `module from Workspace path sys.path was loaded` never appears. A module actually loaded from the Workspace is refused by R7's line, as today in substance. The check that today raises that line is kept under a line of its own: where, at the end of the collection, an entry of the import path that resolves inside the Workspace stands ahead of every entry that resolves inside the copy (the copy's root, a mapped folder, an `import_roots` folder), the run is refused with exit 2 by a line naming that entry and saying that it stands ahead of the copy on the import path, so that a test that puts the Workspace first and imports later is still caught. An entry behind the copy's entries, as an editable install's `.pth` entry stands, refuses nothing.
9. **R9. The checkpoint mode.** `--checkpoint` runs the probe (R1) on the archived copy and reads the roots the same way: a root (mapped or from `import_roots`) whose folder exists in the copy at the commit is used, one whose folder does not is skipped, neither refusing the run nor stopping the judgement. `module_file_at_commit` reads the commit through the same roots (R5).
