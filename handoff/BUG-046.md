# BUG-046: the permission guard's `gh api` merge refusal reads a flag's value as the method, and its file-body refusal holds only for the bare word `graphql` (R-082)

Round cause: first round (no earlier round)

## Objective
Fix the following confirmed defect: repair the named cause, nothing else.

**Root cause, in one sentence:** in `bridge/cursor-bridge/permission-guard.py`, the `gh api` part of `_check_word_list` (lines 2327-2346 as of commit f3fa7b4) takes the request's method from every word of the command (lines 2337-2344), so a method-shaped word that gh reads as another option's value (`-p -XGET`, `-H --method=GET`) is read as the method, and a PUT merge passes; and it refuses a body it cannot read (`--input`, a field read from a file) only where the endpoint word is exactly `graphql` (line 2329), while gh reaches the GraphQL endpoint by its URL or its path as well.

**Evidence** (docs/debug/BUG-046.md, found 2026-11-17 by the security audit of TASK-083's round 4):
1. On main at f3fa7b4, from a folder that is no bridge Workspace, the guard passes under Bash and PowerShell: `gh api -X PUT repos/o/r/pulls/5/merge -p -XGET`, `gh api --method PUT repos/o/r/pulls/5/merge -H --method=GET`, `gh api https://api.github.com/graphql -F query=@q.graphql`, `gh api https://api.github.com/graphql --input body.json`, `gh api /graphql -F query=@q.graphql`; it refuses `gh api -X PUT repos/o/r/pulls/5/merge` and `gh api graphql -F query=@q.graphql`.
2. gh 2.97.0's own help (`gh api --help`): `-p/--preview`, `-H/--header`, `-q/--jq`, `-t/--template`, `-X/--method`, `-f`, `-F`, `--input` take a value; gh's flag parser takes the word after such an option as its value whatever it begins with, so `-X PUT ... -p -XGET` sends PUT. A field value beginning `@` is read from a file (`@-` from standard input); `--input` reads the body from a file or standard input.
3. Both lines stand at commit b05fbc8 (TASK-063's merge): older than TASK-083 and no regression of it.
