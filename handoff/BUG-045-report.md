## Summary

The git help exemption in `_check_word_list` is now true only when the words after the git subcommand are exactly one help word (`-h` or `--help`), or when the subcommand is `worktree` and those words are exactly `remove` followed by one help word. A help word that git reads as an option value or as a word after `--` no longer skips the hooksPath, config, hook-skipper, force-push, or worktree-remove refusals. The alias loop, the refusal texts, and the `gh pr merge` help exemption are unchanged.

## Named cause

The exemption is no longer a membership test for `-h` or `--help` anywhere among the words after `git`; `helpful` is computed from `git_subcommand`'s `args` being exactly one help word, or `remove` and one help word for `worktree`, so a help word that is an argument does not skip those five refusals.

## F1

In `_check_word_list`, line 2322 assigns `helpful` from `sub` and `args` immediately after `git_subcommand(w)` on line 2321, and the alias loop remains on lines 2316-2320; the five refusals that read `not helpful` are on lines 2323, 2325, 2330, 2338 and 2344. Pinned by the nine cases of `test_bug045_a_help_word_git_reads_as_an_argument_exempts_no_refusal`, the six cases of `test_bug045_a_lone_help_word_after_the_subcommand_still_passes`, `test_bug045_premise_git_takes_a_help_word_as_the_message_and_skips_the_hooks`, and the passing run of `tests/test_permission_guard.py` (which includes `git worktree remove --help`).

## F2

- `test_bug045_a_help_word_as_the_file_of_F_is_refused` pins `git commit --no-verify -F -h`: `-h` is the file of `-F`, and the refusal names `--no-verify`.
- `test_bug045_a_help_word_beside_other_arguments_is_the_ruled_over_refusal` pins `git commit --no-verify -a -h -m x` as refused with `--no-verify` in the reason. git would print its help and run nothing, because `-h` stands as its own option beside other arguments; the refusal is the ruled, safe over-refusal.
- `test_bug045_a_config_hookspath_with_a_trailing_help_word_is_refused` pins `git config core.hooksPath /dev/null -h` as refused, with `core.hooksPath` in the reason. `git_subcommand` returns subcommand `config` and args `core.hooksPath`, `/dev/null`, `-h`. F1's rule makes `helpful` false for that `args` (three words, and the subcommand is not `worktree`), so the existing config refusal applies to `core.hooksPath` with value `/dev/null`.
- `--message=-h`: no case was added for `git commit --no-verify --message=-h`. That word is one token, equal to neither `-h` nor `--help`, so neither the old membership test nor the fixed rule treats it as a help word. It does not bear on the help exemption. The hook-skipper reader already treats a `--message=` word as a message and still sees `--no-verify` as the skipper.

No hand mutation was made. No mutation script was written.
