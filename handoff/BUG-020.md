# BUG-020: the loop guard's cron_next misses a one-shot wake-up in the hour the clock repeats

## Objective
Fix the following confirmed defect — repair the named cause, nothing else.

**Root cause (one sentence):** `cron_next(expr, now)` in `bridge/cursor-bridge/loop-guard.py` (lines 203-215) steps through wall-clock minutes (a naive local `datetime` advanced by `timedelta(minutes=1)`) instead of through instants, so on the night clocks go back it passes the repeated hour only once and never matches a one-shot schedule in its second occurrence, and inside that hour it converts the matched naive wall time back with `t.timestamp()`, which resolves an ambiguous wall time to its first occurrence, an hour early.

**Evidence (copied from `docs/debug/BUG-020.md`):** "Hypothesis 1 holds: of four probes only the repeated-hour one failed, and the first-occurrence 02:49, ambiguous as well, was found. A second run at 01:20 UTC, inside the repeated hour itself (02:20 local standard time), showed the same cause's second face: for now + 1,800 s (02:50, the second time) `cron_next` returned 00:50 UTC, the first occurrence, an hour early (3,647 s off), because the walk matched the naive wall time and `t.timestamp()` resolves an ambiguous naive time to its first occurrence. So hypothesis 2's mechanism is real too, but only as a consequence of the walk in wall time: an instant-based walk returns the instant it visited and never converts back. The loop's own structure gives the mechanism: the starting point is the naive wall time 02:36, and every later point is that plus whole minutes in naive arithmetic, which has no fold." The symptom: `tests/test_loop_guard.py::test_the_hook_input_is_read_in_its_live_forms` failed at its one-shot assertion on 2026-10-25 at 00:35 UTC, the night summer time ended on the supervisor's computer (Europe/Berlin), because `cron_next` returned None for a one-shot schedule at a local time in the repeated hour.

**Reproduction test** (supervisor-written; do not edit it), failing today with `TypeError` because `cron_next` takes no `tz` argument, and required to pass after the fix: `tests/test_loop_guard.py::test_bug020_a_one_shot_in_the_repeated_hour_is_found`. It names the zone Europe/Berlin through the new `tz` keyword, so it runs at any hour on any computer that has zone data, and checks five cases: 02:09 the second time, 02:49 the first time and 03:09 on 2026-10-25 (clocks back at 01:00 UTC); 03:30 and 01:45 on 2027-03-28 (clocks forward at 01:00 UTC). With the fix, `tests/test_loop_guard.py::test_the_hook_input_is_read_in_its_live_forms` passes at every hour of the year.

The required behaviour: `cron_next` walks instants one minute apart, starting at the first whole minute after `now`; it reads each instant as a local wall time with `datetime.fromtimestamp(instant, tz)` and matches the five cron fields against that wall time; on a match it returns that instant itself, never a wall time converted back to a timestamp. A new keyword parameter `tz=None` names the zone; `None` means the computer's local zone, which is today's behaviour for every existing caller.

Satisfies: no requirement ID; this is a defect fix outside the build plan's increments (Issues entry ISS-014, diagnosis `docs/debug/BUG-020.md`). It restores the loop guard's stated contract in its own docstring: a scheduled wake-up counts as a wake source at its real time.

## Context
- The function as it stands (`bridge/cursor-bridge/loop-guard.py`, lines 203-215):
  ```python
  def cron_next(expr, now):
      """The next fire time (local wall clock, as a unix time) of a 5-field cron expression, within
      eight days; None when the expression does not parse. Claude Code's session crons are local time."""
      fields = (expr or "").split()
      if len(fields) != 5:
          return None
      t = datetime.fromtimestamp(now).replace(second=0, microsecond=0) + timedelta(minutes=1)
      for _ in range(8 * 24 * 60):
          if cron_field(fields[0], t.minute) and cron_field(fields[1], t.hour) and cron_field(fields[2], t.day) \
                  and cron_field(fields[3], t.month) and cron_field(fields[4], t.weekday() + 1 if t.weekday() < 6 else 0):
              return t.timestamp()
          t += timedelta(minutes=1)
      return None
  ```

## Requirements
1. `cron_next` takes a new keyword parameter `tz=None`. `None` means the computer's local zone; any other value is a `tzinfo` (such as a `zoneinfo.ZoneInfo`). The signature is `cron_next(expr, now, tz=None)`.
2. The walk is through instants: the first candidate is the first whole minute (a unix time divisible by 60) after `now`, and each next candidate is the previous one plus 60 seconds. Each candidate is read as a wall time with `datetime.fromtimestamp(candidate, tz)`, and the five fields are matched against that wall time's minute, hour, day, month and weekday.
3. On a match, `cron_next` returns the candidate instant itself. No wall time is converted back to a timestamp anywhere in the function (no `.timestamp()`, no `mktime`, no arithmetic on a naive datetime).
4. Unchanged, exactly as today: the eight-day bound (`8 * 24 * 60` candidates), the None result for an expression that does not split into five fields, the None result when nothing matches within the bound, the use of `cron_field` for each field, and the weekday rule `t.weekday() + 1 if t.weekday() < 6 else 0` (Monday 1 to Saturday 6, Sunday 0).
5. The docstring says that the function walks instants one minute apart, each read as the wall time of `tz`, that it returns the matching instant as a unix time, and that `tz` is the zone (None for the computer's local zone, the zone Claude Code's session crons are written in).
