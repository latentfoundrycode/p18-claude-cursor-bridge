# CONFIG-B3b: the generated command reference of the bridge's programs

## Objective
The bridge's programs under `bridge/cursor-bridge/` have no machine-readable command reference, so a supervisor who tells the owner to type a command copies it from memory. This increment adds a generator, `tools/dump-cli.py`, that reads every command program's real argument parser (or, for a program that reads its arguments by hand, its module docstring) and writes `docs/cli-reference.json` (the source of truth) and `docs/CLI_REFERENCE.md` (rendered from it for people). It also adds a `--check` mode that CI and the local pre-commit gate run, so a changed command without a regenerated reference cannot merge. The convention is in `~/.claude/cursor-bridge/Delivery-Conventions.md` §4 (you cannot read that path: it is outside the Workspace; everything you need from it is in this brief). This is the last calibration item of 2026-10-19, applied at the start of stage B3. It is not a build-plan increment. It also closes one recorded gap: CI's windowless step does not scan `.cursor/hooks`.

Satisfies: no requirement ID (a calibration item: rule 32, Delivery-Conventions §4). Tests name it `CONFIG-B3b`.

## Context
**Programs.** `bridge/cursor-bridge/` holds 30 `*.py` files. 29 are command programs, each with an `if __name__ == "__main__":` block. One is a library, `bridge_env.py` (no `__main__` block): the reference leaves it out. The commands fall into two kinds:

- **argparse programs (7):** `completion-check.py`, `plan-check.py`, `diagram-check.py`, `inventory-check.py`, `sync-check.py`, `evaluate-reports.py`, `workflow-check.py`.
  - `workflow-check.py` already has a module-level `def build_parser():` that `main(argv=None)` calls (`args = build_parser().parse_args(argv)`). It is the pattern to follow.
  - The other six build their parser inside `main()`, as `ap = argparse.ArgumentParser(...)` followed by `ap.add_argument(...)` lines and then `a = ap.parse_args()`.
  - `evaluate-reports.py` has sub-commands: `sub = ap.add_subparsers(dest="cmd")`, with the parsers `collect`, `record`, `seed`, `extract`. After `parse_args()` its `main()` uses `ap.print_usage()` when no sub-command is given, so its `main()` still needs the parser object after the extraction.
- **hand-parsed programs (22):** `bench-check.py`, `boundary-check.py`, `bridge-check.py`, `bridge-install.py`, `bridge-run.py`, `bridge-stop.py`, `conformance-check.py`, `invisible-check.py`, `lock-check.py`, `loop-guard.py`, `permission-guard.py`, `pr-activity-check.py`, `refactor-check.py`, `review-guard.py`, `roster-check.py`, `run-hidden.py`, `scope-check.py`, `session-start.py`, `shell-guard.py`, `wake-timer.py`, `windowless-check.py`, `worktree-teardown.py`.
  - Each has a module docstring.
  - Five of them are hooks that read a JSON payload from stdin and take no command-line arguments: `boundary-check`, `loop-guard`, `permission-guard`, `session-start`, `shell-guard`. Their docstring describes the hook contract instead of a usage line. They are still commands, and their docstring is their entry.

**Import side effects (checked).** Importing any of the seven argparse programs runs only definitions and constant assignments. Examples: `NO_WINDOW = subprocess.CREATE_NO_WINDOW if sys.platform == "win32" else 0`, compiled regexes, `HERE = os.path.dirname(os.path.abspath(__file__))`, and `evaluate-reports.py`'s `HOME = os.path.expanduser("~")`. **Defaults that would put a computer path in the reference.** `workflow-check.py` lines 47-49 hold these module constants:

Argparse's `prog` (and a sub-parser's prog) defaults to the name of the script that is running, such as `dump-cli.py` or `pytest`. It differs between runs, so a command's name in the reference is its file name, never `parser.prog`.

## Requirements
1. **`tools/dump-cli.py` writes the reference.** Run as `python tools/dump-cli.py` with no argument, it writes `docs/cli-reference.json` and `docs/CLI_REFERENCE.md` and exits 0.
   - It finds the repository as the parent folder of its own `tools/` folder, so it works the same from any current folder, and it reads and writes nothing outside that repository's `bridge/cursor-bridge/` and `docs/` (the tests run it on a copy of the programs in a temporary folder, Acceptance criterion 3b).
   - It covers exactly the 29 command programs: every `*.py` directly under `bridge/cursor-bridge/` that has an `if __name__ == "__main__":` block. It finds them when it runs, not from a hard-coded list, so a new program is covered without editing the generator.
   - It leaves out every library: today `bridge_env.py`.
2. **JSON shape.** `docs/cli-reference.json` is one JSON object written with sorted keys, `indent=2` and a final newline. Its key `"commands"` is a list of one object per command, ordered by `"name"`. Each object has:
   - `"name"`: the file name, e.g. `"plan-check.py"`.
   - `"path"`: the repository-relative path with forward slashes, e.g. `"bridge/cursor-bridge/plan-check.py"`.
   - `"source"`: `"argparse"` or `"docstring"`, the source the entry came from.

   An `"argparse"` entry also has:
   - `"description"`: the parser's description.
   - `"positionals"` and `"options"`: lists of the parser's actions in the parser's own order. Positionals are the actions with no option strings. Options are the rest, the automatic `-h`/`--help` included.
   - `"subcommands"`: a list of `{"name", "description", "positionals", "options"}` objects ordered as the program adds them, or `[]`.

   Each action object carries these keys:
   - `"option_strings"`: a list.
   - `"dest"`
   - `"nargs"`
   - `"type"`: the type callable's `__name__`, or `null`.
   - `"default"`: a JSON value, with Requirement 5 applied.
   - `"required"`
   - `"choices"`: a list, or `null`.
   - `"help"`: or `null`.

   The sub-parsers action itself is represented by `"subcommands"`, not listed among the positionals.

   A `"docstring"` entry also has `"usage"`: the module docstring, whole, exactly as `ast.get_docstring(<module node>, clean=False)` returns it.
3. **`docs/CLI_REFERENCE.md`** is rendered from the JSON alone, for people. Its layout is yours, but it must:
   - list every command by name;
   - for an argparse command, show each argument and option with its default, `required` and choices;
   - for a docstring command, show its usage text.

   It must hold nothing that is not derived from the JSON.
4. **The generator never runs a program.**
   - It never calls a program's `main()` and never starts a subprocess.
   - **Which commands are argparse programs is found from the source, not from a list:** a command is an argparse program exactly when its module defines a top-level `def build_parser():`, found by parsing the file with `ast` (without importing it). Every other command is a docstring entry. A command whose source contains `ArgumentParser` but defines no top-level `build_parser()` makes the generator exit 1, naming the file, and write nothing: such a parser could not be read without running the program. (Today this holds: `ArgumentParser` appears only in the seven argparse programs.)
   - It imports only the argparse programs, under a module name other than `__main__`, and obtains each one's parser by calling its module-level `build_parser()`.
   - It reads a hand-parsed program's docstring without importing it: `bridge-run.py` and `roster-check.py` change `sys.path` at import.
   - The structure comes from the parser's action objects, never from `format_help()`, `format_usage()` or `parser.prog`.
5. **Identical output on every computer and on Python 3.12 and the local Python.**
   - Neither output file contains an absolute path, a drive letter, a user name, a home, profile or temporary folder, or the current folder.
   - A default that is computed from the program's own location, the home folder, the current folder or an environment variable is recorded by a stated placeholder, never by its value on this computer. The two `workflow-check.py` defaults must read exactly `"<bridge folder>/workflow/open-list.md"` and `"<bridge folder>/workflow/extension-points.md"`.
   - If any other default turns out to be an absolute path, the generator exits non-zero, names the program and the option, and writes nothing.
   - Both files are UTF-8 with LF line endings.
6. **`--check`.** `python tools/dump-cli.py --check` regenerates both files in memory and compares them with the committed files, with line endings normalised (a CRLF copy counts as matching). It writes nothing.
   - **Exit 0:** both files match.
   - **Exit 1:** either file differs or is missing. It prints one line per differing file, naming it as `docs/cli-reference.json` or `docs/CLI_REFERENCE.md`.
   - **Exit 2:** a usage error (any other argument), with a usage line, and nothing is written.
7. **CI** (`.github/workflows/tests.yml`, job `tests` only), exactly these two edits and nothing else. No other step is added, removed, reordered, renamed, skipped or given `continue-on-error`, no action is re-pinned, and no other key changes.
   - (a) The windowless step keeps its name, and its `run` becomes exactly `python bridge/cursor-bridge/windowless-check.py bridge/cursor-bridge .cursor/hooks`.
   - (b) A new step is inserted immediately after the step `the manifest matches the tree` and before the workflow-check step, which stays last. It is exactly:
   ```yaml
         - name: the command reference docs/cli-reference.json matches the programs
           run: python tools/dump-cli.py --check
   ```
   (The step's name carries `docs/cli-reference.json` on purpose: the bridge's conformance check recognises the CI currency check by that word in the workflow.)
8. **Pre-commit** (`.githooks/pre-commit`).
   - After the existing windowless check, add a run of `python tools/dump-cli.py --check` that exits 1 with a one-line message on stderr when the check returns non-zero. The message names the regeneration command, `python tools/dump-cli.py`.
   - Keep the file POSIX sh with LF line endings.
   - Update its header comment to say it now runs the command-reference check as well.
9. **`build_parser()` extraction** in `completion-check.py`, `plan-check.py`, `diagram-check.py`, `inventory-check.py`, `sync-check.py` and `evaluate-reports.py`. Each gets a module-level `build_parser()` that builds and returns the same parser its `main()` builds today, and `main()` calls it. This is a pure extraction:
   - the same arguments, defaults, choices, help texts and descriptions;
   - the same exit codes, printed messages and parsing behaviour;
   - `main()`'s signature unchanged (each is `def main():` today).

   Change nothing else in these files. `workflow-check.py` is not touched.
10. **Manifest.** After your last edit to any file under `bridge/`, run `python tools/make-manifest.py` with no arguments from the Workspace root, and commit nothing by hand into `MANIFEST.json`. `bridge/cursor-bridge/VERSION` must come out byte-identical.
11. **Windowless (rule 24).** `tools/dump-cli.py` starts no process. If you find you need one, stop and report it instead. Any launch would need `creationflags=subprocess.CREATE_NO_WINDOW` on Windows (`0` elsewhere), as `windowless-check.py` requires.
12. Generate and commit-ready the two reference files. Do not edit them by hand. Run `python tools/dump-cli.py` after your last parser change.
