# BUG-044: records-migrate.py writes a plan header the headed plan's readers refuse (R-062)

## Objective
Fix the following confirmed defect — repair the named cause, nothing else.

**Root cause, in one sentence:** `_validate_read_back` in `bridge/cursor-bridge/records-migrate.py` (lines 469-484) checks a written header only with `bridge_env.read_header`, `bridge_env.check_header` and `bridge_env.header_agrees` against `fallback_for(...)`, which is the same reading `_compose_plan_header` (lines 276-303) built the header from, so it always agrees with itself and never checks what the headed plan's readers check. Those readers apply two rules that a plan with no header never meets: (a) the shape rule, under which a `### <ID>` heading outside any `## ` stage is refused (`bridge_env.walk_plan_prose_body(body)["outside_stage"]`, read by `bridge_env.plan_header_refusal` at bridge_env.py:3463-3467, `bridge_env.plan_header_findings` at 3510-3518 and `bridge_env.plan_check_parse` at 590-594); (b) completion-check.py's scan outside the header (completion-check.py:223-233), under which every R-id that `bridge_env.plan_r_ids_outside_headers(text)` (bridge_env.py:3273-3294) reads must be in the union of the header's `satisfies`. That function also reads bold lines (`**Satisfies:**`, `**Satisfies**:`, line 3288) and plain `Satisfies:` lines that stand in no increment, neither of which the walker's field pattern `FIELD_RX` reads.

**Evidence** (docs/debug/BUG-044.md, found by stage H2's review, round 1, after TASK-051 and TASK-052 merged), two reproductions:
1. A heading outside any stage. In a plan whose `### TASK-001` stands before its first `## ` heading, `plan-check.py --no-git` gives `RESULT: OK` before the migration. `records-migrate.py` prints `wrote docs/BUILD_PLAN.md` and exits 0, but the header holds TASK-002 only. Afterwards `plan-check.py --no-git` gives `SHAPE: TASK-001 has a ### heading but stands outside any stage`, `DEPENDS: TASK-002 depends on TASK-001, which does not exist`, `RESULT: 3 problem(s)` and exit 1, and `plan_header_refusal` refuses wherever a merge unit is checked.
2. A bold Satisfies line. Take a plan with `**Satisfies:** R-099` beside a plain `Satisfies: R-004`, and `**Satisfies**: R-011` alone in a second increment. `completion-check.py --mode plan` gives `RESULT: OK` before the migration. The migration writes `satisfies: [R-004]` and `[]`, and afterwards completion-check gives `HEADER DISAGREES: satisfies` and exit 1.

**The reproduction tests:** `tests/test_bug044.py`, every case above the line `# ---------------------------------------------------------------- the builder adds its cases below this line and edits nothing above it`. On 86a37e3 they give "6 failed, 2 passed" (the two passing are the guards on the plain plan). These are the 6 that fail and must pass:

The fix, as the supervisor ruled it (F1 to F5 under Requirements):
- Before writing, the migration refuses a plan that its headed readers would refuse, listing it `cannot read <path>: <reason>` with the repair (F1, F2).
- The read-back of a plan also runs those readers' rules, as a second net (F3).
- Two smaller findings from the same review are fixed in this brief too: the root path escaped in the plan glob (F4), and `merge_unit: null` written for a brief with no `Merge unit:` line (F5).

Satisfies: R-062 - Migration is a program: `records-migrate.py` writes each header-less record's header from `bridge_env`'s fallback reading of its prose, atomically and read back before the move, lists and leaves header-less what it cannot read, and the calibration commits its result as a records-only checkpoint, "append-only, reopening no gate". (Full text: R-062's row in `docs/REQUIREMENTS.md`. This brief serves the "reopening no gate" half: a migrated record must pass the checkers it passed before.)

## Requirements
Use the labels F1 to F5 in your report.

1. **F1. 2. **F2. A plan whose header would not hold every R-id its readers read is refused before writing.** Once the plan's header is composed, compute the union of the `satisfies` of every increment in that header. If any R-id that `bridge_env.plan_r_ids_outside_headers(text)` reads is missing from that union, list the plan `cannot read <path>: <R-id> is on a Satisfies line the header would not hold; write each increment's IDs on one plain Satisfies: line under its ### heading`, with `<R-id>` the first missing R-id in that function's order. The reason does not matter: a bold Satisfies line, a Satisfies line in a stage's text before its first `### ` heading, one below a `#### ` heading inside an increment, or a second plain `Satisfies:` line in one increment. The check is this set comparison and nothing else: the program adds no Satisfies pattern of its own. Nothing is written, with or without `--check`, the run goes on and the exit code is unchanged. Tests: `test_bug044_a_bold_satisfies_line_is_listed_cannot_read_and_not_written` and the gate case `[bold-satisfies]`.
3. **F3. The read-back of a plan also runs its readers' rules.** For kind `build-plan`, the check that `_validate_read_back` performs, both in memory under `--check` (line 510) and on the temporary file read back from disk (line 556), also does two things on the decoded new file:

   - it checks that every R-id of `bridge_env.plan_r_ids_outside_headers(decoded)` is in the union of that header's increments' `satisfies`.

   A finding fails the check exactly as a read-back failure does today: the existing failure line, exit 3, the run stopping, the record byte-identical and no temporary file left. A plan that F1 or F2 lets through must never fail here.

Test: `test_bug044_a_glob_character_in_the_root_s_path_still_finds_the_plans`.
5. **F5.
