# TASK-029: One heavy job at a time: the launcher's machine-wide slot

## Objective

On 2026-10-19/20 the owner's computer crashed during a flood of terminal windows. The process-start record put the flood on heavy runs that overlapped or repeated (ISS-011). TASK-028 made every launch windowless. This increment makes heavy runs take turns. A run of `bridge/cursor-bridge/bridge-run.py` of kind `builder`, `test` or `driver` takes one machine-wide slot before its command starts and holds it until the launcher ends. The slot is an exclusive operating-system lock on one byte of `~/.cursor-bridge/heavy.lock`. A second heavy run waits for the slot. While it waits it says once a minute who holds the slot and until when. It never counts the wait against its own ceiling, and it gives up with exit 123 once a bound it fixed at the start of the wait has passed. A `review` or `watch` run takes no slot. `bridge/cursor-bridge/loop-guard.py` learns the `driver` kind and widens how long it counts a launched heavy command, because that command may now wait before it starts. The loop's text that uses all of this (step 3's `timeout`, step 3b's handling of exit 123) is TASK-030's, not yours.

Satisfies: R-040: One heavy job at a time on the computer: a builder run, a test suite and a mutation run each hold one machine-wide slot in the launcher while they run (an exclusive lock on a file under the bridge's state folder in the owner's home, `~/.cursor-bridge/`, where the agent home already lives), which every session and the owner's own programs see alike, released by the operating system the instant the holder ends; a second heavy run waits for it, saying what it waits for, as long as the holder's own ceiling allows and never counting the wait against its own; a review and a CI watch take none.

## Requirements

1. **Which runs take the slot.** A launcher run whose resolved kind is `builder`, `test` or `driver` (the kind resolved as today, including the `test` kind `BRIDGE_RUN_ALLOW_ANY=1` gives an unnamed helper) takes the slot before its command starts and holds it until the launcher process ends. A `review` or `watch` run never opens, locks or reads the lock file or the record. A run refused with exit 125 by an existing check does so before it takes the slot, as today.
2. **The lock.** The slot is an exclusive operating-system lock on one byte of `<home>/.cursor-bridge/heavy.lock`. Use `msvcrt.locking` on Windows and `fcntl.flock` elsewhere. `<home>` is `bridge_env.real_home(os.environ)` of the launcher's own environment (the `USERPROFILE`/`HOME` the launcher was started with). The folder is created when it is missing. There is one lock for the computer, never one under a project, and never under `LOCALAPPDATA`, `APPDATA` or the installed `~/.claude` tree. The lock is never broken, stolen or timed out by a waiter: the operating system releases it when the holder's process ends, so there is no stale lock and no takeover. If the lock file cannot be opened or locked for a reason other than another holder, the run does not start its command. It exits 125 with one line beginning `bridge-run: refused - ` that names `~/.cursor-bridge/heavy.lock` (that literal text, never the absolute path) and the error's class. A heavy run's command never starts without the lock held.
3. **The holder's record.** Once the lock is taken, the holder publishes its record to the sibling file `<home>/.cursor-bridge/heavy.lock.holder`. The record holds its kind, its run id, its pid (the launcher's own), that process's creation time, its `slot taken` time as `start`, and its limit in whole seconds. It is written to a temporary file in the same folder and moved into place with `os.replace`. The publication must succeed even while a waiter is reading the record at that moment (see Context, Pitfalls); a failure to publish after retrying is a note on stderr, never a crash and never a release of the lock. Any other process can read the record while the lock is held, on Windows too. A record counts as live only while a process with its pid **and** its creation time is alive. A record whose process has ended, whose pid now belongs to a process created at another time, or that does not parse or has a field of the wrong type, reads as no record.
4. **The lines of a heavy run.** Every heavy run prints `bridge-run: started <run id>` first, as today. When it takes the slot it prints `bridge-run: slot taken <UTC time>Z` (the format of the run id without suffix), and its command starts only after that line. A run that finds the slot free prints `slot taken` at once and no waiting line. A run that finds the slot held prints, when the wait begins and then once every reporting interval (60 s), one waiting line:
   - with a live record: `bridge-run: waiting for the slot held by <kind> <run id> since <start>Z, ends by <end>Z`, naming the holder of the live record read most recently, where `<end>` is that record's `start` plus its limit plus a grace of 120 s;
   - with no live record: exactly `bridge-run: waiting for the slot held by unknown`.
   The `<start>` and `<end>` times use the run id's format. Every field printed from the record is printed only if it is a plain value of the expected form (a kind among `KINDS`, a run id of the launcher's own form); anything else prints as `unknown`. The waiter tries the lock at least once a second, so a slot freed by its holder's end is taken within about a second.
5. **The wait's bound.** At the wait's start the bound is provisional: the builder's cap (`CAP_FACTOR * KINDS["builder"]`, 14,400 s, never an owner's lifted value) plus the grace (120 s), counted from the wait's start. The first time the waiter reads a live record, the bound is fixed once: that record's `<end>`, but never earlier than the wait's start plus the waiter's own kind's default (`KINDS[kind]`), and never later than the provisional bound. Once fixed, the bound is never recomputed, whatever holders come and go, so a wait never exceeds 14,400 + 120 s. A waiting line that names a later holder does not move the bound.
6. **A wait that ends unmet.** When the bound passes with the slot still held, the run does not start its command. It prints `bridge-run: slot not free - held by <kind> <run id> since <start>Z, ends by <end>Z`, naming the last live record it read and that record's end, or `bridge-run: slot not free - held by unknown` when it never read a live record. Then it prints `bridge-run: exit 123` as its last line and exits 123. The code 123 is distinct from the command's limit (124) and from the refusals (125). Such a run is never marked healthy, by the launcher or by `--healthy` (which refuses it with a `bridge-run: refused - ` line and exit 1, leaving the log unchanged).
7. **The ceiling and the log.** The run's limit is chosen as today, before the wait, and the command's ceiling starts at `slot taken`: the wait never counts against it. Every heavy run's `runs.jsonl` entry records `waited`, the whole seconds between the start of the slot attempt and `slot taken` (0 when the slot was free), apart from `seconds`, which stays the command's own running time. A 123 run's entry records `exit: 123`, its `waited`, and a `seconds` that `learned_limit` cannot learn from. So `--limit auto` learns nothing from a wait. `learned_limit`, `cap_for` and the health rules are otherwise unchanged.
8. **The loop guard.** `loop-guard.py` knows the `driver` kind: the `--kind` pattern in `command_ceiling` accepts `driver`, and `KIND_CEILING` holds the driver's default, 7,200 s, so `--limit auto --kind driver` gives twice that (or the owner's `Ceiling above twice: driver ...` value) instead of the `test` fallback. The `# wake <kind>` form is unchanged (a driver gets no `# wake`, TASK-030). A launched command, meaning one matching `bridge-run\.py`, whose kind (from `--kind`, or the existing fallback) takes the slot (`builder`, `test`, `driver`) counts while its age is at most the heavy launch's one sum plus `GRACE_SECONDS` (600 s). The sum is the command's own ceiling as `command_ceiling` gives it (its explicit `--limit N`, or with `--limit auto` the kind's cap) + 14,400 (the longest wait, the builder's cap) + 120 (the grace) + 60 (the waiter's reporting minute). A `review` or `watch` launch, a `# wake` command and a bare `cursor-agent` command count exactly as today. The module docstring says it in one sentence.
9. **The test-only clock.** The launcher reads one test-only environment variable, `BRIDGE_RUN_SLOT_SCALE`. Unset or empty, nothing changes. Set, it is parsed with `float`. A value that is not a finite number with 0 < value <= 1 is refused before anything starts: exit 125 and one line beginning `bridge-run: refused - BRIDGE_RUN_SLOT_SCALE`. A valid value multiplies every duration of the slot: the reporting interval (60 s), the grace (120 s) in `<end>` and in the bounds, the waiter's own-kind floor (`KINDS[kind]`) and the provisional bound. It never changes the run's limit, the limit written in the record, the lock itself, or which runs take the slot, and it can never let a command start without the lock. The docstring names it as test-only. It is the only way your tests shorten the slot's durations.
10. **Windowless and clean.** Everything the launcher starts stays windowless as TASK-028 left it, and no `windowless: visible-ok` exemption is added. Every process your tests start is windowless: a launch sets no creation flags (the suite's default in `tests/conftest.py` then applies `CREATE_NO_WINDOW` on Windows, and `stdin=subprocess.DEVNULL` when no stream is redirected), or sets them with `CREATE_NO_WINDOW` on the same line, so that `tests/test_tests_windowless.py`'s scan stays empty. Do not rely on any other default. No test leaves a process, a lock or a record behind: every process a test starts (a launcher, or a helper that holds the lock) is killed with its tree and waited for in a `finally`, and its pipes are drained or closed.
11. No new dependency. ASCII-only program text, as both programs say. Numbers from the record, the log and the environment are parsed with `json`, `int` and `float`, never by slicing a string.
