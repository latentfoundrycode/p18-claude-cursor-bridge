# TASK-062: The launcher detects a change of git's configuration (R-081)

## Objective
`bridge/cursor-bridge/bridge-run.py` (the launcher) starts the project's test suites (kind `test`) and the supervisor's drivers (kind `driver`) with the checkout as the working folder. A run of either kind can write git's own configuration in the checkout's `.git` (a `core.fsmonitor` line, a hook, an attributes file) and the session's next git command then runs what it wrote with the owner's login; release T's stage T2 reproduced exactly that end to end with a stripped test that wrote `core.fsmonitor`, and today only text (step 4's read by hand) stands against it. This increment makes the launcher read, before and after every run of kind `test` or `driver`, the bytes of git's configuration files and of every entry of the hooks folders, and print one line `bridge-run: GIT-CONFIG <path> <new|removed|changed>` per difference on standard error, after the run's own output and before the exit line. It is a detection, as BOUNDARY is for builder and review runs, never a restore: the exit code, the log row and the limit are unchanged. The supervisor's acceptance tests are written and committed; your work is to make them pass without breaking the existing ones.

Satisfies: R-081 - The launcher detects a change of git's configuration made by a test or driver run (J17): it reads the repository's `config` and `info/attributes` in its common git folder, the worktree's own `config.worktree`, and every entry of the hooks folders by name and content (the folder `core.hooksPath` names and `.git/hooks`) before and after the run and prints one `bridge-run: GIT-CONFIG <path> <word>` line per difference on standard error, the word `new`, `removed` or `changed`, the run's exit unchanged and nothing restored; step 4 of the loop names the line beside its read of the same files. (Step 4's text is not part of this increment; the launcher's line is.)

## Requirements
1. **Which runs.** The reading and the lines happen for runs of kind `test` and `driver` only (the kind as final after line 2235, so a `BRIDGE_RUN_ALLOW_ANY` run that became `test` counts). Runs of kind `builder`, `review` and `watch` print no GIT-CONFIG line and make no git call for it. A launch folder that belongs to no repository (git cannot name its common git folder) prints nothing.
2. **What is read.** The set of files, fixed before the child starts from git run in the launch folder: `config` and `info/attributes` in the common git folder (`git rev-parse --git-common-dir`, the existing `git_common_dir`); `config.worktree` in the worktree's own git folder (`git rev-parse --git-dir`); and every direct entry of two hooks folders, the folder git uses for hooks before the run (`git rev-parse --git-path hooks`, which resolves `core.hooksPath`; a relative answer is resolved against the worktree's top) and the common git folder's `hooks`. A folder named twice (the usual case: no `core.hooksPath`, both are `.git/hooks`) is read once, so no entry gets two lines; the same holds for the common and the worktree git folder being one folder in a main worktree. Each file and each hooks entry is compared by its bytes through a hash (sha256 is fine): never by size or time.
3. **When.** The before-read is taken after every refusal and after the heavy slot is held, immediately before the child starts, so that a refused run, a run whose slot is not free (exit 123), and a driver refused at its last check (lines 2390 to 2398) make no git call (the existing test of Context, `tests/test_bridge_run_driver.py` line 376, holds this), and a change another run makes while this one waits for the slot is not reported as this run's. The after-read is taken after the child has ended or been stopped at its limit, before the exit line.
4. **The after-read takes no instruction from the run.** It reads exactly the paths and folders the before-read fixed, listing the same hooks folders again, and makes no git call. A hooks folder named only after the start (a `core.hooksPath` set during the run) is not read; that change shows as `.git/config changed`.
5. **The line.** One line per difference, on standard error: `bridge-run: GIT-CONFIG <path> new` for a file or hooks entry absent before and present after, `removed` for present before and absent after, `changed` for present both times with other bytes. Absent before and after, or the same bytes: no line. A read that fails (a path that exists and cannot be read as a file's bytes, for instance a folder standing where the file was, or a permission error) gives `bridge-run: GIT-CONFIG <path> unreadable`, and that path gets no other line; every other path's line stands. `<path>` is relative to the folder that holds the common git folder (its parent), with forward slashes: `.git/config`, `.git/info/attributes`, `.git/hooks/pre-commit`, `.githooks/pre-commit`, `.git/worktrees/<name>/config.worktree`. A path that does not lie under that folder (an absolute `core.hooksPath` elsewhere, another drive) still gets its line, never an exception: your choice of its form, stated in the report. The lines come in a fixed order (your choice, stated), each written once.
6. **Where.** The lines are written after the run's own output and before `bridge-run: exit <n>`, which stays the last line of standard error (review-guard reads it): on the normal path beside `report_boundary()` at line 2463, and on the limit path beside `report_boundary()` at line 2447, before the exit line and before `killer()` ends the process, flushed. A child that itself exits 124 within its limit (line 2462: no exit line today) also gets its GIT-CONFIG lines after its output; whether and when the exit line prints for it does not change.
7. **Nothing else changes.** The exit code is the child's (or 124 at the limit) whether or not a line prints; the log row gets no new field and its values are as without this increment; the limit and the learned limit are untouched; nothing is restored, removed or rewritten in `.git` or a hooks folder; no option and no environment variable is added. Any failure of the reading itself (git missing, a timeout, a git folder that vanished, an exception in the comparison) never stops the run, never changes its exit code or its row, and never raises out of `main()`: at most the lines it could not compute are missing. Every git call is windowless (`creationflags=NO_WINDOW`), bounded by `bridge_env.GIT_TIMEOUT`, with its output captured.
8. **Bounded reading.** A hooks folder's direct entries only are read (no walk into sub-folders); an entry that is itself a folder is never hashed recursively. How such an entry is treated is your choice, under one condition: a run that changes nothing in that folder prints no line for it (a folder present before and after is not reported on every run). State the choice in the report.
9. **Your own cases** in `tests/test_bridge_run.py`, each naming R-081 (in its name, docstring or a comment), each launching in a scratch repository of its own under `tmp_path` (never the checkout), with `GIT_CEILING_DIRECTORIES` set to its `tmp_path` and a timeout on every subprocess call: (a) the limit path: a test run whose child writes `.git/config` and then outlives a short `--limit` prints `.git/config changed` before `bridge-run: exit 124`, which stays the last line, exit code 124; (b) a child that itself exits 124 within its limit after adding a hook prints that hook's `new` line; (c) without `core.hooksPath` a hook added gives exactly one line (the folder read once); (d) a refused run (for instance a `--kind driver` whose program is not under `run/supervisor/`, or a command the launcher refuses) prints no GIT-CONFIG line and leaves its repository's `.git` as it was. You may add more.
10. **The manifest** is regenerated with `python tools/make-manifest.py`; `VERSION` is unchanged; `python tools/dump-cli.py --check` stays clean (the module docstring does not change).
