# BUG-002: The workflow check accepts spacing the `Workflows:` grammar does not allow

## Objective
Fix the following confirmed defect — repair the named cause, nothing else.

**Root cause (one sentence):** in `bridge/cursor-bridge/workflow-check.py`, `check_head` strips each `→`-segment and each comma-split name before its shape check compares them with the open list's names, so a head whose spacing differs from the grammar (no space or two spaces around the arrow, a leading space after `Workflows: ` or after `<part>: `, a trailing space before `; traits: `) passes as if it were spelled exactly.

**Evidence** (found independently by both reviewers of stage B2; cause proven by reading the code; `bridge/cursor-bridge/workflow-check.py` as it stands today):

```python
def check_head(head, path, tables, findings):
    segments = [segment.strip() for segment in head.split("→")]
    names_by_seg = [[name.strip() for name in segment.split(",")] for segment in segments]
    ...
    if len(subs_found) == 0:
        shape_ok = names_by_seg == [[types_found[0]["Workflow name"]]] and not traits_in_head
    else:
        shape_ok = (
            names_by_seg == [[types_found[0]["Workflow name"]], [subs_found[0]["Sub-workflow name"]]]
            and not traits_in_head
        )
    if not shape_ok:
        findings.append(("form", path, "-", "Workflows head is not the product type, then at most its sub-type"))
```

The grammar this violates is `bridge/commands/supervisor.md`, section "Project state", the **Workflows** paragraph (line 1819): `Workflows: [<part>: ]<Workflow name>[ → <Sub-workflow name>]; traits: <Trait name>[, <Trait name>…]`, every name "spelled exactly as `~/.claude/cursor-bridge/workflow/open-list.md` spells them". The stripping was commissioned by TASK-006's brief (`handoff/TASK-006.md`, Requirement 11.4: "split on `→`, each segment stripped, and each segment split on `,`, each name stripped"); the rest of the line is already exact: `check_traits` splits on exactly `, ` and does not strip, and `prefix_of` makes a part name with surrounding whitespace `form`. `inventory-check.py` and `conformance-check.py` judge the line through `check_status`, so they inherit the defect and inherit the fix without change. There is no `docs/debug/BUG-002.md`; the evidence above is the whole of it.

**Reproduction tests** (supervisor-written and committed; do not edit them):
- `tests/test_workflow_check.py::test_r015_separators_are_exact` — 6 parametrized cases (`arrow-unspaced`, `two-spaces-before-arrow`, `two-spaces-after-arrow`, `two-spaces-after-colon`, `space-before-traits-mark`, `two-spaces-after-part`), all failing today; each must pass after your change (exit 1 and at least one `FAIL (form) ` line).
- `tests/test_workflow_check.py::test_r015_exact_separators_pass` — the control, 2 cases (`single`, `with-part`), passing today; must still pass.

Satisfies:

## Context
- `check_head(head, path, tables, findings)` (`workflow-check.py` line 602) receives `head`, the text between `Workflows: ` (or `<part>: `) and `; traits: `, exactly as written in the status file: `check_status` (line 678) takes `rest = line[len("Workflows: "):]`, `prefix_of(rest, multi)` (line 577) removes `<part>: ` on a multi-line file and returns the remainder untouched, and `head, traits = body.split(TRAITS_MARK, 1)` with `TRAITS_MARK = "; traits: "` (line 84). Nothing upstream strips. So for the six failing cases `head` is, respectively, `Host Extension Development→Claude Code Extension`, `Host Extension Development  → Claude Code Extension`, `Host Extension Development →  Claude Code Extension`, ` Host Extension Development` (leading space), `Host Extension Development ` (trailing space) and ` Web App Development` (leading space, the `app:` line).
- The lookup tables come from `load_tables` (line 246): `tables["workflow_by_name"]` maps a product type's **Workflow name** to its open-list row (keys `Key`, `Name`, `Workflow name`, `Written`); `tables["sub_by_name"]` maps a **Sub-workflow name** to its row (keys `Key`, `Of type`, `Sub-workflow name`, `Written`); `tables["trait_by_name"]` maps a trait **Name**.
- Findings are 4-tuples `(code, path, name, reason)` appended to `findings`. The ones `check_head` emits today, which keep their code, name and reason text exactly: `("form", path, "-", "empty name in the Workflows head")`; `("unknown", path, name, "name is not in the open list")`; `("e", path, "-", "part must name exactly one product type")`; `("e", path, "-", "part must name at most one sub-type")`; `("e", path, <Sub-workflow name>, "sub-type is not of the line's product type")`; `("form", path, "-", "Workflows head is not the product type, then at most its sub-type")`; `("f", path, <Workflow name>, "product type is not written")`; `("f", path, <Sub-workflow name>, "sub-type is not written")`.

## Requirements
1. In `check_head`, once the counts are right (exactly one product type, at most one sub-type, and that sub-type is of the product type — today's `counts_right`), `head` must equal exactly the product type's Workflow name, or exactly the Workflow name + `" → "` + the sub-type's Sub-workflow name. `" → "` is one space (U+0020), the arrow U+2192, one space; no other character may stand before, after or between. The comparison is on `head` as received, character for character: no stripping, no case folding, no Unicode normalization.
2. Any `head` that fails Requirement 1 when the counts are right yields the existing finding `("form", path, "-", "Workflows head is not the product type, then at most its sub-type")`, once, as today.
3. The name-by-name lookups that produce `unknown`, the empty-name `form`, the two `e` count findings, the crossed-pair `e` finding and the two `f` findings stay, with the same codes, names, reasons and order of emission as today. When the counts are not right, `check_head` still returns before the shape test, as today.
4. A head with a trait Name in it, the sub-type first, or an empty segment still yields the shape `form` (it can no longer equal the exact text, so Requirement 1 covers it).
5. No other function in `workflow-check.py` changes, and no other file under `bridge/` changes except `MANIFEST.json` through `tools/make-manifest.py`.
