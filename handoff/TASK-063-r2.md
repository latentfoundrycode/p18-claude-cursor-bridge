## Requirements
1. **One reader.** One iterative scan (a loop with an explicit stack; no recursion that grows with the input's nesting) reads the command once and yields, for every context, its simple commands. In this brief **a substitution** means `$(...)`, a backtick pair, `<(...)` and `>(...)`, never `${...}`. The contexts:
   - top level;
   - single quotes: no escape, the next `'` closes;
   - double quotes: a backslash escapes only `"`, `\`, `` ` ``, `$` and a newline; the reader walks past a `\x` pair, never counting backwards;
   - ANSI-C `$'...'`: `\'` and `\\` escape; locale `$"..."`: as double quotes;
   - `$(...)`, and `<(...)`/`>(...)` outside double quotes only (inside double quotes they are text): quoting starts fresh inside, as at top level; a `(` inside it (a subshell, `$((`) opens a level its own `)` closes; inside it the reader follows `case ... in ... esac`, so a pattern's `)` closes nothing;
   - a backtick pair: its end is found first, at the first backtick not escaped by `` \` `` (a `\\` is one escaped backslash), whatever quote, `${` or `#` comes before it; then its body, with `` \` ``, `\\` and `\$` unescaped, is read fresh as commands (so `` echo `echo "` ; git worktree remove ../Worktrees/TASK-012 ; `echo "` `` refuses the removal, as bash runs it);
   - `${...}`: to its matching `}`; inside it only quotes and substitutions are read, never a comment and never a separator (`echo ${x:- #} ; git worktree remove ...` runs the removal in bash).

   Outside single quotes a backslash makes the next character literal (it starts no quote, no substitution, no comment and no separator), and the parity of a run of backslashes is carried forward, never recounted. A `#` that starts a word at top level or inside a substitution begins a comment to the end of the line (or, inside a backtick pair, to its end); anything in it is text. An unclosed substitution runs to the end of the text and its body is read as commands, never a character dropped; an unclosed quote runs to the end as text (bash runs nothing on a line whose quote never closes).
2. **Separators.** At top level and inside a substitution, `&&`, `||`, `;`, `|`, a newline and every single unquoted `&` that is not part of `&&`, `>&`, `&>` or `<&` end a command, with or without spaces around it. `split_commands` also ends a command at a subshell's `(` and `)`; `chain_parts` keeps a pipe inside one part, as built.
3. **Both splitters and every check from the one reading.** `split_commands` returns the top-level commands and the commands of every substitution at any depth, each once (no level read twice); every refusal meets each. Rule 8's chain: a line is a chain when its top level, or the body of any substitution in it, has two or more parts; a part changes state when it, or a command inside one of its substitutions, does; so `ls && echo "$(git commit -m x)"` and `echo "$(git add -A && git commit -m x)"` in a Workspace are refused. Never flatten a substitution's commands into its parent's parts (that would make the app's single commit command a chain). The rule that refuses a chain starting with `cd` reads the top level only (`echo "$(cd "$(dirname "$0")" && pwd)"` is not that refusal). The app's commit form (`git commit -m "$(cat <<'EOF'` ... `EOF` newline `)"`, with or without `--no-verify` and a checkpoint subject) still passes in a Workspace and an apostrophe in its body opens no quote.
4. **Here-documents.** The reader knows `<<` and `<<-` only outside quotes in the current context (a `<<` inside `$(` counts) and never `<<<` (a here-string, whose word is read as a word, its substitutions as commands). The delimiter word loses its quotes as bash removes them (`'EOF'`, `"EOF"`, `\EOF`, `E"O"F` are all `EOF`, and each is a quoted delimiter); several here-documents on one line are read in order, their bodies one after another. A body runs to the line that is exactly its delimiter (after leading tabs for `<<-`), or to the end of the text where none comes. A body is data, except: with an unquoted delimiter bash expands it, so it is read as double-quoted text (its substitutions are commands: `cat <<EOF` newline `$(git worktree remove ../Worktrees/TASK-012)` newline `EOF` is refused); and where a shell reads it, a wrapper shell (`WRAPPER_SHELLS`) as the command that holds the `<<` or as a later command of the same pipeline (`cat <<EOF | bash`), its lines are read as commands. A quoted delimiter's body read by no shell is pure data. `commit_message` still gets the here-document's first line as the subject.
5. **Linear time and a bound.** The whole reading is linear in the command's length; no regular expression that can backtrack runs over the whole line (the known sites: `HEREDOC_RX`, used by `strip_heredocs` and `commit_message`, and `chain_parts`' `re.sub(r"^\(+|\)+$", ...)`, about 2.3 s on 40,000 `)` inside quotes); no line is sliced at every character. One bound you choose (at least 64) holds the reader's stack and `check`'s own recursion through `eval`, wrapper shells, `find -exec` and `xargs` together: `check` may keep that recursion if it is held to the bound. A command past it is refused with a reason that says it nests too deeply to read. Every case of the acceptance file finishes well under 15 seconds.
6. **Words.** `words()` decodes `$'...'` as bash decodes it, every escape with its digit counts: `\'`, `\"`, `\\`, `\?`, `\a`, `\b`, `\e`, `\E`, `\f`, `\n`, `\r`, `\t`, `\v`, `\cX`, `\nnn` octal (1 to 3 digits, `$'\55\55force'` is `--force`), `\xHH` (1 or 2 hex digits), `\uHHHH` (1 to 4), `\UHHHHHHHH` (1 to 8); and reads `$"..."` as a double-quoted word, so a subcommand, a flag or an option spelled in them is read as bash reads it.
7. **`HUSKY=0`.** The checkpoint's test is kept on the parsed command: a leading `HUSKY=0` assignment (after other assignments, and after `env` with its options and their values, `VALUE_OPTIONS["env"]`) is refused when the words after the assignments hold `git` followed by `commit`, `push` or `merge`, through any runner (`HUSKY=0 setsid git commit -m x`, `HUSKY=0 winpty git push origin main`, `HUSKY=0 python -c "import os; os.system('git commit -m x')"`: the last holds the words inside its quoted argument, which is the checkpoint's test). A quoted `&`, a redirection (`2>&1`, `&>file`) and `&&` are not this refusal. `echo gh api a&b` is not a gh command.
10. **The graphql test** reads the `gh api graphql` command's own words: refused when one of them holds a substitution the reader finds (unquoted or inside double quotes), wherever the command stands. A single-quoted `$(` is text, so `gh api graphql -f query='$(x)'` passes: a deliberate change from the checkpoint, which refused it by reading the raw line (the query is on the command line, which is what the refusal asks for).
11. **The tool.** `check(command, cwd=None, tool="Bash")`; `main()` passes the tool name; every recursive call (`eval`, a wrapper shell, `find -exec`, `xargs`) keeps the outer tool.
