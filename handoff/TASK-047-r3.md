# TASK-047-r3: The status file's header in its six readers, round 3 (a part named twice)

## Objective
Fix the following confirmed defect — repair the named cause, nothing else. This is the third round of TASK-047, the review ceiling, and it carries exactly one defect: Review A, round 2, finding B1, of the behaviour class. Nothing else from the round-2 reviews is this round's work; the findings the Out of scope section names go to the supervisor's HARDENING record.

**Root cause.** `bridge_env.status_workflow_line` (`bridge/cursor-bridge/bridge_env.py` lines 2286-2305) returns at once when a `Workflows: ` line names a part a second time (lines 2293-2294, `if seen_parts[part] == 2: return part, body_line, None, [STATUS_WORKFLOWS_PROBLEMS[2]], None`), so it never checks that line's `'; traits: '` count or its empty names.

**Evidence.**
- `status_workflows` therefore drops the second line's other grammar problem: its problems list holds only `two Workflows lines name the same part`. Round 1's inline loop collected both, the duplicate first. You can read round 1's loop as the removed lines of `git diff b039f96 0261674 -- bridge/cursor-bridge/bridge_env.py`.
- `workflow-check.py`'s `check_status` (lines 678-706) treats a line whose only reported problem is the duplicate wording as fit to read further, and goes on to `head, traits = body.split(TRAITS_MARK, 1)` (line 703):
  - with no `'; traits: '` marker, the unpack fails and the program ends with a `ValueError` traceback;
  - with two markers, the split keeps the second marker inside the traits text, and `check_traits` prints a false `not a trait name` finding in place of the traits wording;
  - with an empty name, workflow-check prints the empty-name wording (from `check_head`) while `status_workflows` does not report it, so the two readers disagree.

**The reproduction tests**, all in `tests/test_header_status.py`, in its `# --- round 3` block just above the builder's marker line. All six fail on 0261674 today and must pass:
- `test_r058_r3_a_part_named_twice_keeps_the_second_lines_other_problem`, over the ids `no-traits-mark`, `empty-name` and `two-traits-marks`;
- `test_r058_r3_workflow_check_refuses_a_part_named_twice_as_bridge_env_does`, over the same three ids.

**The required behaviour**, from Requirement 3 of round 2's brief (`handoff/TASK-047-r2.md`):
- `workflow-check.py --status` refuses exactly what `status_workflows` refuses, with the same wording.
- A part named twice adds no part, and its line's other grammar problem is still reported, after `two Workflows lines name the same part`.
- workflow-check never splits a body that breaks the traits rule.
- workflow-check's `FAIL (<code>) <path>: <name> - <reason>` format, its codes and its part names stay as they are. Its other, non-grammar findings (such as `Workflows head is not the product type, then at most its sub-type`) may still appear.

Satisfies: R-058 - The status file's header (`phase`, `workflows`, `awaiting_user_on`, `bridge_version`, `stage`, `open_issues`, typed as the design's table states them) is read first by every program that reads the file.
