# BUG-046 round 3: the merge endpoint is a word that names both pulls and merge (R-082)

Round cause: security

Blocking class: safety mechanism - Review A and the security audit of round 2, each reproduced in process under both tools: gh api -X PUT 'repos/o/r/pulls/5/%23/../merge' and gh api -X PUT 'repos/o/r/pulls/5/%3F/../merge' pass round 2's guard while gh sends the escaped delimiter inside the path, which resolves to the merge endpoint; round 1's tree refused both

## Objective
Replace the merge-endpoint rule's reading of the path with one that cannot be split by any delimiter, and nothing else.

This is round 3 of BUG-046, at the review ceiling. Rounds 1 and 2 each read the merge endpoint by a parse of the word (round 1: dot segments resolved over the whole word; round 2: the word decoded, then cut at its first `?` or `#`, then resolved), and each next review found a spelling the parse reads apart from gh (round 2: an escaped `%3F` or `%23`, at any nesting, which gh keeps inside the path, so the `..` after it is never seen; and an escaped `%2F` read as a separator). The family has now been met twice, so the design changes instead of the parse growing: **a `gh api` word is a merge endpoint when its decoded, lower-cased text holds both `pulls` and `merge`.** A request GitHub routes to `/repos/<o>/<r>/pulls/<n>/merge` must carry those two names in its one endpoint word, in some spelling that decodes to them: a dot segment only removes whole segments, a query or fragment adds nothing to the path, and an escape decodes to its letter. No cut, no resolution, no segment reading is then needed. The supervisor commits round 2's tree together with this brief and the new tests before your run, so the line numbers below hold when you start.
