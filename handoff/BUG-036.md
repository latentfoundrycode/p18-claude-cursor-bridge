# BUG-036: the review guard counts release B's builder rounds as Review B rounds

## Objective
Fix the following confirmed defect: repair the named cause and nothing else. Root cause: when an increment has no rounds record, `_seed_rounds` in `bridge/cursor-bridge/review-guard.py` seeds as many replied Review B rounds as the highest `<N>` of the tracked `handoff/<ID>-r<N>[letter]-report.md` files (`_report_file_rounds`). Since release 2026.10.11d every builder round writes such a report, so under release B the guard counts builder rounds as Review B rounds. Evidence: release B's trial on another project (2026-10-30). The installed guard (release 2026.10.30a) refused an increment's first Review B with `review-guard: refused - round 1 is off the count (current 3)`. That increment, BUG-004 there, had three builder rounds, each sent back by Review A before any Review B. Its first Review B could only be named `-r4`, which is above the three-round ceiling, so it could never reach its cross-family review. With one builder round, the first snapshot is refused `round 1 is reviewed: write <ID>-r2`. The mechanism, in the code at HEAD: `load_rounds` (line 577) seeds a missing `rounds-<ID>.json` through `_seed_rounds` (lines 529-552), which takes `max(letter_n, report_n)` and writes rounds 1..n with `"reply": 0` and `"seeded": True`. `snapshot_review_refusal` (lines 642-706) then treats every seeded round as counted (line 673, "off the count") and as reviewed (lines 675-683, a round with a reply). The governing text says the guard counts Review B rounds, never builder rounds. Merge-Verification-Policy.md says "review-guard.py, which counts the Review B rounds". `bridge/cursor-bridge/workflow/phases/delegation-loop.md` step 8 says "<N> the round it opens: one more than the rounds the guard has counted for the increment". delegation-loop/decide.md, "The review ceiling", says the guard's count and the launcher's count "move independently". Report files are seeded only to cover an increment already in flight when release B was installed. See CHANGELOG 2026.10.30a, Running projects must ("the ID's first snapshot seeds it"), and docs/INVENTORY.md, the R-042 row ("seeds an increment in flight from its letter snapshots and report files"). Reproduction: `tests/test_bug036.py`, written by the supervisor before your run. All 3 of its tests fail on the current tree and must pass: `test_bug036_three_builder_rounds_under_release_b_open_review_round_one`, `test_bug036_one_builder_round_under_release_b_first_snapshot_is_round_one` and `test_bug036_rounds_before_the_install_still_seeded_rounds_after_it_not`. Read the file whole before you start. It imports its helpers from `tests/test_task032_supervisor_guard.py`.

Satisfies: R-042, the code gate's round ceiling held by programs. The clause concerned (docs/REQUIREMENTS.md, the R-042 row): "an increment in flight when the release installs is counted from its snapshots and its builder reports". The guard's count is "the guard's count of rounds opened for the increment", meaning the Review B reads that `review-guard.py snapshot <ID>-r<N>` opens.

    pat = re.compile(r"^handoff/%s-r(\d+)[a-z]?-report\.md$" % re.escape(id_part))

## Requirements
1. A release-B builder row for a report `handoff/<ID>-r<N>[letter]-report.md` is a row of `bridge_env.read_runs_jsonl(bridge_env.launcher_log_folder(common, root))` that meets all three of: `kind` equal to `"builder"`; `brief` equal to the ID (`id_part`); `round` an int (not a bool) equal to that report's `<N>`. A row matches whatever its `exit`, `healthy`, `branch`, `brief_name` or other fields are.
2. A report file counts toward the seed only if its round has no release-B builder row. The seed from report files is the highest `<N>` among the tracked report files whose round has no such row, or 0 if there are none.
3. Everything else in the seed stays exactly as it is: the letter-snapshot count (`_letter_snapshot_rounds`), `n = max(letter_n, report_n)`, the refusals of `_seed_refuse_snapshots` and their order (they still come first), the tracked-file listing and its pattern (letter suffixes included), and the seeded entries' shape (`reply` 0, `seeded` True, `tree` "", `time` "", `lift` None, the names and branch as today). Every other rule of the guard is unchanged.
4. As a result, an increment whose builder rounds all ran under release B seeds nothing from its reports, and its first Review B is round 1 under its bare name or `-r1`. An increment in flight at an install, built before it, seeds as it does today. A mixed increment seeds only the rounds built before the install. A builder row of another ID never affects this ID's seed.
5. A missing or unreadable launcher log means no release-B rows: every report counts, as today. No new refusal, exit code or output line is added.
6. Neither function carries a comment or docstring today. You may add one short comment at `_report_file_rounds` or `_seed_rounds` stating the rule ("a report counts only for a round with no release-B builder row"). Add nothing longer.
