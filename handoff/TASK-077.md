# TASK-077: The evaluation's security step as a program

## Objective
Every Sunday the bridge's maintainer session reads each project's weekly dependency-scan workflow, its runs and its open Dependabot alerts by hand, using `gh`. This increment turns that reading into a subcommand of `bridge/cursor-bridge/evaluate-reports.py`: `security`. It reads each project by GET alone, through the bridge's one `gh` seam, under a time limit and windowless. It writes `Reports/Evaluations/<date>/security.md` with one section per project, of one of the kinds the design defines (a finding, a scanner failure, no completed run, not configured, no remote) or green. A read that fails is a finding with its remedy, never an empty section and never green. Of a job's log, only the scanner's exit line enters the file. The reading window per project is kept in the ledger's `_meta`, and it moves only after the file is written. The project roots also move. Today `evaluate-reports.py` holds four drive-letter paths in its `PROJECTS` dict. Those move to a per-computer file, `~/.cursor-bridge/projects.json`, which `collect`, `extract`, `seed`, `record` and `pace-report.py` read too. When that file is absent, the program names it, says what it holds, and stops.

Satisfies: R-097: The Sunday evaluation's security step is a program (C13). `evaluate-reports.py security` reads, for each of the bridge's projects and by GET alone, the weekly workflow's state, its runs since the last read and the open Dependabot alerts. It writes `Reports/Evaluations/<date>/security.md` in the three kinds release T's design defines, and green. A read that fails is a finding with its remedy, never an empty section. No log text beyond a step's exit line enters the file. The window's state stands in the ledger's `_meta`. The project paths stand in the per-computer file `~/.cursor-bridge/projects.json`, which `pace-report.py` reads too; the program names that file and stops where it is absent. The evaluation command's step 1b names the program. (That last clause is TASK-078's text increment, not yours.)

## Requirements
1. **The command.** `python ~/.claude/cursor-bridge/evaluate-reports.py security [--date <YYYY-MM-DD>] [--seed-from <evaluation file>]`. It writes `Reports/Evaluations/<date>/security.md` under `bridge_root()`, `<date>` defaulting to today. `--date` is parsed with `datetime.date.fromisoformat` after a `YYYY-MM-DD` shape check; a value that fails is usage (exit 2). `security` is the fifth subparser, after `extract`, and has no option beyond these two. The module docstring gains the command line in its usage block and names the subcommand, `--seed-from`, and `~/.cursor-bridge/projects.json` with its form. It says what the step reads, what it writes, and that it makes GETs only.
2. **The projects file.** `~/.cursor-bridge/projects.json` holds a JSON object of project name to project root (an absolute folder holding `Workspace/`). The home is resolved when the file is read, not at import, from `os.path.expanduser("~")`. One reader in `evaluate-reports.py` returns the dict or a refusal, and every caller uses it.
   - Absent: one line naming `~/.cursor-bridge/projects.json` and saying that it holds a JSON object of project name to project root; exit 2.
   - Malformed: not JSON; not an object; an empty key; a value that is not a string. Each is refused with its reason, naming the file; exit 2.
   - Either way nothing is written (no folder, no file, no ledger change) and no read is made.

   `collect`, `extract`, `seed` and `record` read the same file where no `--project-root` is given, with the same refusal and exit 2. With `--project-root` they read the one project as today, and the file is not read.
3. **PROJECTS goes.** The `PROJECTS` dict and every drive-letter path leave the program: code, strings and the docstring alike. `tests/test_program_security_step.py` scans every token but comments, the docstring included. `WORKSPACE_KEY_ONLY = ("Bridge",)` and the name rule of `project_keys` stay. The root rule compares the root with `bridge_root()` instead of `PROJECTS["Bridge"]`, both normalised with `os.path.normcase(os.path.abspath(...))`. An ordinary project still gets two keys. `project_keys`' signature is unchanged.
4. **The repository.** A project's GitHub repository is the `origin` remote of `<root>/Workspace`, in its https form (`https://github.com/OWNER/REPO` with or without `.git`) or ssh form (`git@github.com:OWNER/REPO` with or without `.git`). The owner and the repository each must match `[A-Za-z0-9_.-]+` before they enter an API path. A git call that reads the remote runs windowless (`creationflags=bridge_env.NO_WINDOW`), with `stdin=subprocess.DEVNULL`, a 30-second limit and one attempt. Any of these makes the project `no remote`, and no `gh` call is made for it:
   - no Workspace checkout;
   - no `origin`;
   - an origin that is not GitHub's or does not match;
   - git failing or timing out.
5. **The reads.** Every GitHub read is `bridge_env.GH_COMMAND + ["api", ...]` by GET. Never pass `-X`/`--method`, `-f`/`-F`/`--field`/`--raw-field`/`--input`, `--jq`/`--template` or `--slurp`; the program parses every reply itself. Each call is one attempt with the limit `bridge_env.GH_API_TIMEOUT` (30 s) and no retry. A timeout is a failed read (R7). The reads, per project with a remote, in this order:
   - (a) `repos/OWNER/REPO/actions/workflows`, through `bridge_env._gh_get`.
   - (b) Where (a) lists a workflow whose path ends in `/dependency-scan.yml`: `repos/OWNER/REPO/actions/workflows/dependency-scan.yml/runs?created=>=<day>`, through `bridge_env._gh_get`. `<day>` is the day (`YYYY-MM-DD`) of the entry's `last_run_read` where that holds a time, else `_meta.last_extract`. A `per_page` query is allowed.
   - (c) For each run of the window whose conclusion is `failure`: `repos/OWNER/REPO/actions/runs/<run id>/jobs`, through `bridge_env._gh_get`. Then, for each job of it whose conclusion is `failure`, `repos/OWNER/REPO/actions/jobs/<job id>/logs` (plain text).
   - (d) `repos/OWNER/REPO/vulnerability-alerts`: 204 means the alerts are on, 404 means `alerts off` and (e) is not made.
   - (e) After a 204 only: `repos/OWNER/REPO/dependabot/alerts?state=open` with `--paginate`.

   No log is read for a run that did not fail. (c), (d) and (e) use the program's own call, because `_gh_get` refuses a reply that is not JSON. That call follows `_gh_get`'s pattern: `capture_output=True`, `stdin=subprocess.DEVNULL`, `creationflags=bridge_env.NO_WINDOW`, `timeout=bridge_env.GH_API_TIMEOUT`, one attempt, nothing raised. How you tell 204 from 404 from a failure is yours to read from what the stand-in and the fixtures give: the exit code and the body's `status`, or the status line of `-i`/`--include`. List what you inferred under Assumed, not verified. Without `--slurp`, `gh api --paginate` prints each page's JSON array one after another. The program reads one or more concatenated JSON arrays (a `json.JSONDecoder().raw_decode` loop over the text) and joins them.

   Where (a) lists no dependency-scan workflow, the project is `not configured`, and (b) and (c) are not made. Where the workflow's `state` is not `active` (`disabled_inactivity`, `disabled_manually`, any other), the project is `no completed run` whatever its runs show. You decide whether (b) is still read for a disabled workflow; state it in the report.
6. **The kinds**, per project, as step 1b and the design define them:
   - **finding**: a completed run of the window ended `failure` and its job log's exit line reads `exit 1`. The remedy names a `DEP-<nnn>` increment (the merge policy's procedure). A finding stands from section to section until a later run ends `success`; a success later in the same window clears it. A standing finding is reported, by its run id, beside whatever kind the week's own runs show.
   - **scanner failure**: the window's last completed run proved nothing. That is a `failure` with another exit code or with no exit line, or a conclusion other than `success` and `failure` (`cancelled`, `timed_out`, `startup_failure`, `skipped`, `action_required`, `neutral`, `stale`). The remedy is exactly `gh workflow run dependency-scan.yml --repo OWNER/REPO`, with the real owner and repository.
   - **no completed run**: the workflow is disabled, with the remedy `gh workflow enable dependency-scan.yml --repo OWNER/REPO`, then the rerun command. Or no run of the window is listed, with the rerun command as the remedy. Or only runs queued or in progress, with no remedy: the next Sunday reads them.
   - **not configured**: no dependency-scan workflow listed. The remedy is the project's calibration item (the configurator adds the workflow).
   - **no remote**: R4.
   - **green**: the window's last completed run ended `success` and no finding stands.

   The words `green` and `Green` appear only in a green section, never as `not green` or in a remedy.
7. **A failed read** is any of: a non-zero exit other than (d)'s 404, a 403, a timeout, gh unable to start, or a reply that cannot be parsed. It is a finding in that project's section, with a fixed phrase per kind of failure and its remedy. The remedy is the login's scope: name `gh auth refresh -s <scope>` with the scope the read needs, never a token. For (d) and (e), add the repository's Security tab as the fallback. A failed read never leaves an empty section and is never green. `_gh_get`'s `reason` and any gh stderr or GitHub message text never enter `security.md` or the program's printed output. A failed read in (a), (b) or (c) leaves the project's ledger entry exactly as it stood. A failed read in (d) or (e) does not change the window.
8. **The log.** From a job log, only a line whose text after the runner's timestamp is exactly `dependency-scan: OSV-Scanner exit <digits>` counts as the exit line, its digits parsed with `int`. These are no exit lines: the script's own listing (where the words stand before `$code`, wrapped in escape bytes), `OSV-Scanner exit 128: no lockfile was read`, and anything else. No other text of the log, and no escape byte, enters the file. Writing the exit code or the exit line itself is optional. You decide how several failed jobs or several exit lines in one run combine; list the choice under Assumed, not verified.
9. **The alerts.** Each open alert is named in its project's section by its `number`, its package (`dependency.package.name`) and its advisory (`security_advisory.ghsa_id`). With alerts on and none open, the section says that no alert is open, on one line containing the word `alert`. `alerts off` (a 404 on (d)) is a finding of its own, beside the scan's kind.
10. **The file.**
    - One section per project in the projects file. Each heading names its project once, and no other heading of the file names any project.
    - Each section holds the project's kind and remedy, the repository `OWNER/REPO` (where it has one), `last run read: <createdAt or none>`, `finding standing: run <id>` while one stands, and the alerts' line.
    - The file is ASCII with no control character but the line feed (carriage returns allowed).
    - Every value taken from a reply, a name or the projects file is reduced to printable ASCII on one line before it is written (non-ASCII as backslash escapes, like `pace-report.py`'s `_ascii_name`).
    - Never an empty section.
11. **The window**, in `Reports/ledger.json` at `_meta.security`, an object of project name to `{"last_run_read": <createdAt string of the newest completed run read, or null>, "finding_standing": <run id or null>}`.
    - The window is the listed runs created later than `last_run_read`, compared as times parsed with `datetime` (not as strings).
    - An entry whose `last_run_read` is null takes every listed run.
    - A project with no entry and no seed takes the runs created on a later day than `_meta.last_extract`. Where `_meta.last_extract` is absent too, you choose, and list the choice under Assumed, not verified.
    - Where the window holds no completed run, `last_run_read` keeps its value.
    - All other ledger keys and `_meta` keys are kept as they are.
12. **The order.** The ledger moves only after `security.md` is written. If the write fails (for example, a file stands where the evaluation folder must be), the ledger stays byte-identical and the exit is non-zero, without a traceback.
13. **`--seed-from <file>`** reads a hand-written evaluation's Dependency scan table: the rows carrying a backticked `OWNER/REPO` and a backticked `last run read: <createdAt or none>`. It seeds `_meta.security` from them only for projects with no entry yet, matched by the project's repository (R4). `none` seeds null. A time is parsed with `datetime`, and a value that does not parse seeds nothing for that row. A `--seed-from` file that cannot be read is usage: one line naming it, exit 2, nothing written, no read made. The seeded entries are saved with the run's window, after `security.md` is written (R12).
14. **Exit codes for `security`.** 0 when `security.md` is written, whatever findings it holds. 2 for usage and for the projects file. Non-zero (1, through `main`'s `OSError` path or the same code) for a failed write. Update the docstring's exit list.
15. **pace-report.py.** With no roots, it reads the projects from the same file through `evaluate-reports.py`'s reader (through `er`, loaded as today), then adds the bridge root as today, de-duplicated. An absent or malformed file is one line naming `~/.cursor-bridge/projects.json` (and the reason where malformed), with exit 2. With roots given, the file is not read.
