**The code as it stands** (round 5's tree at HEAD, line numbers verified):
- `_LINE_DIFF_MAX = 1024 * 1024` (810), used once, in `_blob_text_lines` (889-890): `if len(data) > _LINE_DIFF_MAX: raise ScanError("a file too large to compare")`.
- `_read_blob(oid)` (859-863) runs `git("cat-file", ["blob", "--end-of-options", oid])` and raises `git cat-file failed (exit %d)` on a non-zero exit.
- `classify_blob(data)` (866-878) returns `"utf-16"` where the bytes begin with `FF FE` or `FE FF` and `data[2:]` decodes strictly in that byte order (`utf-16-le` or `utf-16-be`); else `"binary"` where a 0x00 byte stands in `data[:8000]`; else `"text"`. This is F1: an even-length plain-text body after a mark decodes strictly as UTF-16 and is read only so.
- `_blob_text_lines(data, kind)` (888-899): the size check (889-890); for `"utf-16"` it decodes `data[2:]` strictly and raises `the patch cannot be read` on failure (893-896); otherwise `data.decode("utf-8", "replace")`; then `_patch_lines(text)`. `_patch_lines` (379-385) splits on LF and drops one trailing CR from each line.
- `_preimage_lines(oid, mode)` (902-909) returns `[]` for an all-zero id or mode `160000`, else reads and classifies the blob, `[]` for binary, else `_blob_text_lines`.
- `_added_positions(pre_lines, result_lines)` (912-919) runs `difflib.SequenceMatcher(None, pre_lines, result_lines, autojunk=False)` on the whole lists and collects the result positions of its `insert` and `replace` opcodes. No trimming, no work bound (F4).
- `line_diff_added(record, result_data, result_kind)` (922-937) returns `(1-based line, text)` pairs: the result lines, then for each `(oid, mode)` of `zip(record["ids"][:-1], record["modes"][:-1])` the positions against that preimage, intersected (`common = common & positions`); with no preimage, every line.
- `_type_change_addition(record, sections)` (951-976) requires exactly two sections, a deletion (result id all zero, no added line) and an addition (`pre_ids == [zero]`), each matched to the record's ids, and returns the addition.
- `_by_class(record, section)` (979-989) reads and classifies the result blob: binary returns `([], 1)`; text whose section has hunks returns its `added` lines; a result id equal to any preimage id returns `([], 0)`; otherwise `line_diff_added`. It is called with `section is None` where git printed no section, so a merge record with no section takes the line diff today (F2).
- `_lines_for_record(record, sections)` (992-1014): the `T` branch first (993-995: `addition = _type_change_addition(record, sections)` then `return _by_class(record, addition)`), before the deleted-result branch (1000-1005) and the `160000` check (1006-1011, which matches the index line and returns the one section's `added` lines, or `([], 0)` with no section); then the index match and `_by_class` (1012-1014). The `T` branch reading a blob before the `160000` check is F3.
- `_content_by_path(records, sections)` (1017-1033) groups sections by path (a section whose path is not listed raises `the patch and the file list disagree`), calls `_lines_for_record` per record and totals the binary count.

## Requirements
1. **L1. A marked blob.** A blob whose first two bytes are `FF FE` or `FE FF` (a marked blob) is never classified binary and is read in two views, both by the line diff, its section's hunks never used (its section is still matched to its record and its `index` line checked as K3 says):
   - the NUL-removed view: the blob's bytes with every 0x00 byte removed, then decoded as the patch lines are (UTF-8 with replacement), split on LF with one trailing CR dropped as `_patch_lines` does;
   - the UTF-16 view: the bytes from offset 2 decoded in the mark's byte order (`FF FE` little-endian, `FE FF` big-endian) with `errors="replace"`, split the same way.

   Pairing: each view of the result is diffed against the same view of each preimage. A marked preimage gives its two views; an unmarked text preimage (no 0x00 byte in its first 8000 bytes) stands as its bytes (decoded as the patch is) for both views; a binary preimage (unmarked, a 0x00 byte in its first 8000 bytes), an absent preimage (an all-zero id) or a gitlink preimage (mode `160000`) contributes no line. An unmarked text result that takes the line diff is diffed against a marked preimage's NUL-removed view (and against an unmarked text preimage's bytes, as now). A match in either view is a hit, placed by that view's 1-based line number; the same hit (one file, one line number, one kind) found by both views is reported once: the line-diff functions return one entry per result line number, its text the views' texts for that line joined by `"\n"` where they differ (as `kinds_of_parts` joins parts; no path or name matches across a `\n`), so `scan_commit`'s hit loop, unchanged, prints one hit per kind for that line. No refusal and no reason is added. The removal of NULs applies to marked blobs only: an unmarked blob with a 0x00 byte in its first 8000 bytes stays binary and counted.
2. **L2. Records git prints no section for.** A merge record (two or more parents) git lists with no patch section reads nothing. A single-parent record (a root commit counts as one parent) with no patch section raises `ScanError("the patch and the file list disagree")`, after L3's check (a result of mode `160000` is taken first) and after the deleted-result check (an all-zero result reads nothing, as now). A section with no hunk whose result id differs from every preimage id takes the line diff (L1's views for a marked result), its `index` line matched to the record as K3 says. The `Binary files` wording decides nothing.
3. **L3. Mode 160000 first.** A result of mode `160000` is handled first, before any blob read, for every status: for `T`, `_type_change_addition`'s two-section check stays and the addition section's added lines are read unclassified; for a combined status, the one section's added lines are read (as the existing submodule branch, 1006-1011, does). A gitlink preimage contributes no line to any view. Symbolic links (mode `120000`) stay classified and read.
4. **L4. The line diff, bounded.** For each preimage-result pair (per view): trim the common leading lines and the common trailing lines one to one (never overlapping); if the trimmed middles' product (`len(pre_middle) * len(result_middle)`, a count of line pairs) exceeds 1,000,000, or the run's total of such products already diffed plus this one would exceed 10,000,000, run no matcher for that pair and count every line of the result's middle as added against that preimage; else run `difflib.SequenceMatcher(None, pre_middle, result_middle, autojunk=False)` on the middles and map its positions back to the result's lines. The intersection over preimages stands as decided (a result line counts where it is added against every preimage, position by position), taken within each view; the views' added lines are then united (and merged by line number as L1 says). The run's total is one value for the whole run (every commit, record, view and preimage), starting at 0; a pair that is over-read adds nothing to it. The bounds come from a measurement of the worst shape (repeated short lines cost `SequenceMatcher` cubic time: 1,000 by 1,000 lines 2.4 s, 3,000 by 3,000 68 s on this computer), so they are line-pair counts, not a time. The 1 MiB bound (`_LINE_DIFF_MAX` and its check) and the reason `a file too large to compare` are removed; the closed list of reasons returns to round 2's (Context), and no reason added by round 5 remains.
5. **L5. Everything of rounds 1 to 5 that L1 to L4 do not change stays:** K1 to K9 except what L1 to L4 change (in particular K5's rule that a result whose id equals a preimage id reads nothing, and K6's note), H1, G1-G7, F1-F10, R1-R12, the owner's decision of 2026-11-18, the disagreement check, the note, `quote_path`, the short hash, the hit format, the exits.
6. **L6. The accepted limits** (Out of scope) are not handled otherwise.
7. **L7. No change to the command reference.** The module docstring and the parser's description and help stay byte-identical; `docs/cli-reference.json` and `docs/CLI_REFERENCE.md` stay out of Scope and unchanged.
