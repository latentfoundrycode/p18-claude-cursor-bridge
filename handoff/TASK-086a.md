# TASK-086a: The roster resolves an alternate reviewer (R-107)

## Objective
`bridge/cursor-bridge/roster-check.py` resolves which models fill the builder, Review A and Review B roles. Today it reads only the model of the branch's last builder run (`built_by`, line 135) and, where the chosen profile's `review_b` is of that model's family, resolves with a REBUILD entry (lines 616 to 619 and 669 to 671); a profile whose `review_b` is excluded by an exhausted pool or a mark is skipped. This increment makes the program read the **set of families that built the branch** from the launcher's run record (`run/launcher/runs.jsonl`), tell a set that is known, unknown, or cannot be read at all, and resolve by the design's ten-row table: `review_b`, or a profile's new second reviewer `review_b_alt` with a `deviation` entry and a DEVIATION line, or REBUILD, or the profile skipped, or exit 1. It adds two modes, `--repair-record` (moves the record's lines that do not parse aside) and `--review-alt <reason>` (the alternate on request). The launcher (`bridge-run.py`) is **not** edited by this increment: TASK-086b writes the run record's new keys `start_commit` and `clean` and changes the launcher's two review refusals. The supervisor's acceptance tests are written and committed (`tests/test_improve_roster_alt.py`, commit e31d3e5); your work is to make them pass without changing any answer the checkpoint gives that the existing tests read.

## Requirements
1. **R1. One function for the built set.** One function of `roster-check.py` returns, for the current branch, the set of families that built it, or that the set is unknown (with its cause or causes), or that it cannot be read (with its cause). Every builder row of the branch (`kind` `builder`, `branch` equal to the current branch) counts, whatever `brief` it names; a row with `"slot": "not free"` never counts; a row without `brief` always counts. TASK-086b's launcher will call this same function; give it a signature it can call with the record's path and the folder the branch is read in, and state that signature in your report.
2. **R2. The drop rule.** A counted row is dropped only where a later builder row of the branch reads `clean` exactly `true` (JSON `true`, nothing else) and a `start_commit` that is the earlier row's own `start_commit` or an ancestor of it, by git's own answer (`git merge-base --is-ancestor` or an equivalent yes or no). A row without `start_commit`, or whose `start_commit` names no commit of the repository, is never dropped and drops nothing. git's yes or no is the test; any other failure of git is a set that cannot be read (R4). No report file enters this test. `clean` is read from the row as TASK-086b writes it; the program does not look at the working tree to judge it.
3. **R3. A folder in no repository.** Where neither the working folder nor a folder above it holds a `.git` entry, the set is the empty one, as on the checkpoint, and the record is not read for a branch. This is found by looking for the `.git` entry, never by git failing: where a `.git` entry is found and git does not answer, R4 applies.
4. **R4. A set that cannot be read.** Inside a repository the set cannot be read where the head is detached; the record exists and cannot be opened (a folder of that name, for example); git does not answer (it does not start, times out, or fails); or the tree holds a report file (a file under `handoff/` whose name ends `-report.md`, committed or still in the working tree, untracked included) and the branch's base cannot be found (its merge base with `origin/main`, or with `main` where the repository has no remote). The resolve (and `--review-alt`) then ends with exit 1, prints the cause naming `detached`, the record's file name `runs.jsonl`, `git`, or `main` as the case is, prints no `REBUILD` and no `RESOLVED`, and leaves the resolved file unchanged. This row is read before every other. A tree that holds no report file needs no base, so a repository without `main` that holds none resolves as on the checkpoint. A record that does not exist is an empty record.
5. **R5. An unknown set.** Where it can be read, the set is unknown where a line of the record does not parse (as a JSON object), or where a report file that the branch adds over that base has no builder row of the branch for its brief (the brief read from the report's name: `handoff/TASK-001-r1-report.md` belongs to brief `TASK-001`). A report already in the base adds nothing. So a branch that adds no report file and has no record has the empty set, and one that adds a report and has no record an unknown one. Every resolve on an unknown set, whatever it resolves, prints each cause on a line of its own holding `unknown` and `runs.jsonl` or the report file's name, a line that does not begin with `REBUILD`, `RESOLVED` or `DEVIATION`.
6. **R6. The table.** Each profile is judged by the design's table (Context), in the profile order as today: `review_b` where the set is known and `review_b`'s family is not in it; the alternate with `deviation` reason `family` where `review_b`'s family is in the known set and the alternate is independent (its family in neither the known set nor Review A's) and usable (its pool not exhausted, not marked unavailable, and, where probing, it answers its probe); REBUILD with the profile's builder, as today, where `review_b`'s family is in the known set and no alternate is named, independent and usable; the alternate with reason `unavailable` where the set is known, a mark or its pool excludes `review_b`, and the alternate is independent and usable; the profile skipped as today, never a REBUILD, where a mark or its pool excludes `review_b` and no alternate is independent and usable, or the set is unknown; with the set unknown, the alternate never resolved: `review_b` where it is usable and its family is the family of no builder the roster file names (any profile's `builder`, and a v1 roster's top-level `builder`) and of no builder row of the branch that parses, REBUILD otherwise.
7. **R7. Three families stay.** A profile's builder, Review A and `review_b` stay of three families (the collision skip at line 610 stands, an alternate never rescuing a collision); `review_b_alt` may be of the builder's family (the native profile names its own builder model as its alternate). A `review_b_alt` whose family is unknown is not independent.
8. **R8. The deviation entry and line.** Where the alternate resolves, the resolved file's `review_b` is the alternate, it carries `deviation` with `review_b_alt` (the model id), `reason` (`family`, `unavailable` or the reason given), `branch` (the current branch) and `built` (the known set's families as a list), and no `rebuild`; the check prints a line beginning `DEVIATION`. A resolve that needs no alternate writes no `deviation`, so a deviation written before a rebuild is gone after it. Two identical resolves leave the file's bytes unchanged (the existing comparison apart from `resolved_at`), so the entry holds nothing that changes between them (keep `built` in a fixed order).
