The supervisor reproduced it (run/supervisor/probe_latin1_067.py) and found the same pass in an ISO-8859-1 text file's added line; a message with no `encoding` header is converted to UTF-8 by git itself and is found. Security with a stated path (commit content and the user's git configuration, both outside input), older than round 6, not a regression; round 7 is lifted by its class line.
- **Decision: the rule for a segment changes, not the decoding shape by shape.**
  1. **A path's segment begins** with a letter, a digit, `_`, `.`, `-`, or any non-ASCII character that is not whitespace (`str.isspace`), in every path form (a drive, `/Users/`, `/home/`). A byte no decoding reads (U+FFFD under replacement, a lone surrogate under `surrogateescape`) is non-ASCII, so a path whose segment starts with one is found in a message, an added line, a view of a marked file or a file's name alike. ASCII punctuation and the space still begin no segment, so code naming a bare drive (`"C:\\"`) and the placeholder `<name>` still pass.
  2. **A commit object is decoded in the encoding git records for it**: where its header holds an `encoding` line naming an encoding Python's codecs know and that reads ASCII as ASCII, the object is decoded in it, else as UTF-8, with replacement either way, as now. A searched name holding a non-ASCII letter in such a message then matches as written.
  3. **Accepted limit** (R-087, DESIGN C2): a non-ASCII name in text written in an encoding other than UTF-8 that git does not record (a file's lines, a message without a header that git did not convert) is not matched; a path in it is found by (1).
- **Reasoning.** The pass came from one rule meeting every decoding at once: whatever the scan cannot decode it replaces with a non-letter, and the segment rule asked for a letter. Widening the rule to every non-ASCII character makes the decoding irrelevant to paths, as the second resolution made git's view of a file irrelevant, and needs no list of encodings; ASCII punctuation keeps its meaning, so no new false hit falls on code that names a drive. Names cannot be matched without knowing the encoding, so the scan uses the one record git keeps (the header) and names the rest a limit. A narrowing of what passes, so a notice to the owner (rule 58).

## 2026-11-18 TASK-067: a marked file read without its NULs, merges read by git's own rule, the line diff bounded, the second resolution round (R-087)

- **Question:** how the decided design (the entry below) is corrected for round 5's three regressions, each found by a reviewer and each caused by round 5: F1, a file beginning with a UTF-16 byte-order mark but holding plain text (or UTF-16 with a UTF-8 append) read only as UTF-16, its path line passed with no note (the security audit, security); F2, a clean merge of a text file over 1 MiB sent to the size bound and refused, and slow under it (Review A, behaviour); F3, a type change to a submodule read as a blob, exit 2 (both); and F4, the line diff's unbounded time (both, advisory). A second fix that regresses goes to a resolution round (decide.md, "Stop"); handoff/RESOLUTION-TASK-067.md, "The second resolution", holds the findings, both proposals and both votes.
- **Votes.** Review B: the proposal with changes (a byte-order-mark file that fails to decode refuses; a match only in the byte view refuses as ambiguous; a merge with no section reads nothing, a section with no hunk takes the line diff; the result's mode `160000` first; bound the line diff now). Review A: the revised proposal with changes: a hit, not a refusal, for a byte-view match; and an ordinary Windows sequence still passes (PowerShell 5.1 `>`, an odd-length Git Bash `>>`, then a PowerShell `>>` appending UTF-16 at an odd offset: no view at the mark's parity reads it), so it asked for a third view at the other parity; trimming and over-reading in place of the 1 MiB refusal, since an untrimmed bound refuses a one-line edit of an ordinary 0.7 MB UTF-16 file for good; a single-parent record with no section refuses.
- **Decision: the design changes, not shape by shape.**
  1. **A marked blob** (its first two bytes `FF FE` or `FE FF`) is never counted as binary and is read in two views, each by the line diff, its hunks never used: the bytes with every NUL byte removed, decoded as the patch is (UTF-8 with replacement), which reads ASCII text in UTF-16 of either byte order at any offset and any plain-text tail alike; and UTF-16 in the mark's byte order from offset 2, decoded with replacement, which reads non-ASCII text. A match in either view is a hit, each placed by its own view's line number (the two agree for UTF-16 and for ASCII, since a NUL removal removes no LF), never a refusal; no reason is added. Each view of the result is diffed against the same view of each preimage (an unmarked text preimage stands as its bytes for both views; a binary, absent or gitlink preimage contributes no line), and an unmarked text result read by the line diff is diffed against a marked preimage's NUL-removed view. The same hit found by both views (one file, one line number, one kind) is reported once. The removal of NULs is applied to marked blobs only: an unmarked blob with a NUL in its first 8000 bytes is binary and counted, as decided.
  2. **A merge record git lists with no section reads nothing** (Review B's argument, verified by Review A, octopus included: git's dense combined diff drops a hunk only where every change in it comes from one parent, so a line added against every parent always prints). A single-parent record with no section ends with `the patch and the file list disagree`. A section with no hunk whose result differs from every preimage takes the line diff, its `index` line matched to the record; the `Binary files` wording decides nothing.
  3. **A result of mode `160000` is handled first**, for every status, before any blob read: for `T` the two-section check stays and the addition's lines are read unclassified; for a combined status the one section's added lines are read; a gitlink preimage contributes no line. Symlinks stay classified and read.
  4. **The line diff is bounded and never refuses**: each preimage-result pair is trimmed of its common leading and trailing lines one to one before the matcher; where the trimmed middles' product exceeds 1,000,000, or the run's total of products already diffed would exceed 10,000,000, no matcher runs for that pair (an over-read pair adds nothing to the total) and the whole result middle counts as added against that preimage (an over-reading: never a pass; a false hit only where a line already in the parent stands inside a large, scattered change). The 1 MiB size bound and its reason `a file too large to compare` are withdrawn: with trimming and the work bounds they guard nothing and refuse ordinary files.
  5. **Leads** (docs/HARDENING.md): classification reads batched or bounded to a prefix (about 20 ms per changed blob today, each read under git's time limit, failing closed); UTF-32 and UTF-16 of the other byte order inside a marked file; a non-ASCII name in UTF-16 of the other byte order at an odd offset.
- **Reasoning.** Rounds 4 and 5 each found the next shape of the same question (how bytes become lines); a third view would be the next shape again. Removing NULs from a marked blob reads every ASCII run in it whatever its byte order, offset or mix, which is where paths and the owner's ASCII names stand, and the one UTF-16 view keeps non-ASCII text read; neither depends on git's view of the file. Over-reading in place of refusing keeps every outcome a read: a refusal on an ordinary file is a false result every time, an over-read only where a large scattered change holds an old line. The bounds come from a measurement of the worst shape on this computer (Python 3.12, the round-6 brief's read): on repeated short lines `SequenceMatcher` with `autojunk=False` costs cubic time (1,000 by 1,000 lines 2.4 s, 2,000 by 2,000 20 s, 3,000 by 3,000 68 s), so a product bound of 50,000,000 allowed minutes per view; 1,000,000 per pair holds a crafted pair to about 2.5 s per view and 10,000,000 a run to about 25 s, while an ordinary one-line edit trims to a middle of a line or two. The accepted limits narrow: a marked binary is read as text (its false-hit chance is a path-shaped run in its bytes).

## 2026-11-18 TASK-067: content decides how the pre-push scan reads a file, a resolution round (R-087)

- **Question:** how the pre-push scan decides which files it reads line by line, so that no commit content can hide a text file's added lines, no real binary gives a false hit, and a merge's combined diff is read as an ordinary commit's diff is (handoff/RESOLUTION-TASK-067.md, its candidates, both reviewers' votes and the proposal).
- **Why a resolution round.** Round 3's split was ruled first: Review A approved round 3 and the security audit failed it on a committed `.gitattributes` marking a text file `-diff` or `binary`, which hid its added lines behind `Binary files differ` and gave `push-scan: OK`; commit content is untrusted (D-004) and the result a false pass of R-087, so the finding was ruled blocking security, the replace refs (`refs/replace`) riding with it, and round 4 was lifted by that class line, which both reviewers confirmed. Round 4 added `--text` and `--no-replace-objects`; both reviewers rejected it on B1 (a merge's combined diff ignores `--text`, so the hiding stood for merges: security) and B2 (`--text` read real binaries, whose bytes matched the path patterns about 1.5 times per MB: a regression round 4 caused). A class line never lifts a round for a regression its own fix caused, so the design went to the two reviewers.
- **Votes.** Review B, first: none (A as written lets a local attribute force a real binary into text hunks; classify every file by content first). Review A: A extended, adding the UTF-16 route (Windows PowerShell 5.1 `>` and `Out-File` write UTF-16LE, which git shows as binary), full ids, and the submodule and deleted-file exemptions. Review B, second, on the supervisor's proposal: the proposal with changes, its blocking point that a set difference loses a duplicate added line (a parent `P, base`, a result `P, base, P`: git marks the last `P` added, the set holds it present).
- **Decision: content decides; how git shows a file never does.**
  1. The patch read is `git --attr-source=<the empty tree> -c core.attributesFile= show --cc --full-index` with the options it has, without `--text`; the empty tree's id from `git hash-object -t tree` of empty input. A git without `--attr-source` fails the call, exit 2. The file list is `show -z --raw --no-abbrev -M` under the same options, replacing `--name-status`; its parser checks the record's framing, modes, status, the count of ids, each id's length (the repository's hash, `rev-parse --show-object-format`) and lower-case hex, and a path listed twice, any of them wrong ending the scan with exit 2; paths are compared losslessly, never by a replacing decode.
  2. A patch section with hunks or a `Binary files` line carries an `index` line whose ids are the raw record's (one preimage per parent, a root commit's one all-zero preimage, then the result), else exit 2; a deleted file (an all-zero result) holds no added line, else exit 2; a section with neither (a pure rename or mode change) needs no `index` line.
  3. Every result that is neither deleted nor a submodule (mode 160000, whose `Subproject commit` lines are read as today) is read with `git cat-file blob` and classified: UTF-16 where it begins with `FF FE` or `FE FF` and the rest decodes strictly in that order; else binary where a NUL stands in its first 8000 bytes (git's own rule, reproduced in Python, since no git option turns off `.git/info/attributes`; git's size threshold left out of it); else text. A failed read ends with exit 2.
  4. A text result whose section shows hunks is read from its hunks, as today. A text result whose section shows no hunk (git showed it as binary, by any local setting, or listed no section for it) while its result differs from every preimage, and every UTF-16 result whose result differs from every preimage however it is shown, is read by line diffs: the result's lines (split on LF; UTF-16 decoded first) diffed against each preimage, each blob decoded by its own class (UTF-16 as UTF-16, text as the patch lines are), a binary or absent preimage contributing no line, and a result line counts where it is added against every preimage, position by position, so that a duplicate added line counts (the combined diff's own meaning); each hit is placed by its line in the result. A text or UTF-16 blob larger than 1 MiB that needs a line diff ends the scan with exit 2 (a file too large to compare), never a pass. A type change is one record and two sections, a deletion and an addition, the addition read by class. The `Binary files ... differ` wording decides nothing.
  5. A binary result's hunks, where a local setting forced them, are never read; each binary result is counted in `push-scan: note - <n> binary file(s) not read`, which names none.
  6. Accepted limits, in R-087 and DESIGN C2: a path compiled into a binary, a text file with a NUL in its first 8000 bytes and no UTF-16 byte-order mark, UTF-16 without a byte-order mark, and UTF-32 or other encodings are counted or read as their bytes, not decoded; a binary that begins with a UTF-16 byte-order mark and decodes strictly is read as UTF-16 text, its false-hit chance negligible.
- **Reasoning.** Every attribute route (a committed `.gitattributes`, a user attributes file, `.git/info/attributes`, a driver's `binary`, `core.bigFileThreshold`) changes only how git shows a file, so deciding by the bytes of the result makes all of them irrelevant: a forced binary can no longer give a false hit and a hidden text file can no longer pass. Reading a text file shown as binary, rather than refusing it, never blocks a push on a local setting and never passes the file. Line diffs per preimage, not a set, keep git's meaning, a line new against every parent, with its multiplicity. The remaining limits were already unread in rounds 1 to 3 (git showed those files as binary); naming them is a narrowing of what passes, so it is a notice to the owner (rule 58), not a question.
- **Process.** The first Review B vote's error file was named after the round, not the snapshot, so `review-guard.py verify` raised GATE-INTEGRITY on it alone (the file held the launcher's three lines; the tree was restored; no merge rests on that snapshot); the second vote ran under the matching name `TASK-067-r2` and verified OK, so the pull request's Review B round is `TASK-067-r3`. Recorded in docs/HARDENING.md, TASK-067.
