# BUG-042 — the conformance check reads the weekly scan as the gate

Found by stage T2's review, round 1 (Review A's ci part, its B1, a REJECT; the bridge part named the same line as a Consider; Review B silent), reproduced there on scratch projects. Read from `bridge/cursor-bridge/conformance-check.py` at origin/main 1f50cdf and shown by the reproduction tests the supervisor wrote first, in `tests/test_bug042.py`, which fail there for the reason given.

**Symptom.** A project's gate with no OSV-Scanner step, beside the weekly `dependency-scan.yml` that release T puts in every project, reads `OK` on the floor `OSV-Scanner in the gate`; so does a gate whose step is guarded by `if:`. Each reads `MISSING` without the weekly file. The weekly file's pinned download also hides the `OSV-Scanner version pinned` NOTE for an unpinned gate step. It bites once the release delivers the file: a calibration would read a gate with no scanner as conformant.

**Confirmed cause.** `main()` reads every workflow under `.github/workflows/` as the gate: `steps` is extended from every one of them and `scanner_lines` is taken from `wf_text`, the join of all of them, so the unguarded OSV-Scanner step of the weekly file alone satisfies the floor. The weekly file is a second workflow, R-052's own word, and answers for no floor of the gate.

**The fix.** A file named `dependency-scan` with the extension `.yml` or `.yaml`, in any case, is left out of the gate's workflows; the scanner rows and the steps the guarded-step test reads take the rest. The other readers stay on every workflow: the actions-pinned, runner, design-detector and command-reference rows on the whole text, and the two Socket hazard rows (`Socket runs without its banner`, `Socket CLI installed without the key`) on every workflow's steps, since a key in the weekly file's log is a key in a log whatever the file is for.

**Round 2: a regression in round 1, from the supervisor's own brief.** Requirement 1 of `handoff/BUG-042.md` made every reader of `steps` gate-only, which blinded the two Socket hazard rows: a Socket step in the weekly file, with its banner on or its key in the install's environment, read as silence where it had read `MISSING`. The security audit reproduced it; Review A called it contrived. REVIEWERS DISAGREE, on correctness and not intent; decided for the fix, as a regression of this diff on a file a builder can write, one list costing nothing, the rows existing for any workflow. `handoff/BUG-042-r2.md` splits the lists.

**What this does and does not hold.** The exclusion is by the file's name, so a copy of the weekly steps under another name reads as a gate, which is the right reading of a workflow nobody named a scan, and a gate renamed `dependency-scan` reads as no gate, which fails closed. It reads no trigger: a workflow under another name with only `workflow_dispatch`, a job-level `if:`, `continue-on-error`, a comment or an `echo` holding the scanner's name still read `OK`, as they do at origin/main, a program lead in `docs/HARDENING.md`. Nothing checks the weekly file against the frozen block, the conformance floor the CHANGELOG names for the maintainer.
