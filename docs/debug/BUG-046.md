# BUG-046: the permission guard's `gh api` merge refusal reads a flag's value as the method, and its file-body refusal holds only for the bare word `graphql` (R-082, R-083)

Found 2026-11-17 by the security audit of TASK-083's round 4 (docs/HARDENING.md, TASK-083, ruling 2), in code older than TASK-083 and untouched by it. Ruled its own increment, run next after TASK-083 merged as f3fa7b4 (PR #176), before TASK-065.

## Reproduction

On main at f3fa7b4, from a folder that is no bridge Workspace, `bridge/cursor-bridge/permission-guard.py`'s `check(command, cwd, tool)` returns None (passes) under Bash and PowerShell for each of:

- `gh api -X PUT repos/o/r/pulls/5/merge -p -XGET`, `gh api --method PUT repos/o/r/pulls/5/merge -H --method=GET`, and the same with `-q` or `-t` holding the method-shaped word;
- `gh api https://api.github.com/graphql -F query=@q.graphql`, `gh api https://api.github.com/graphql --input body.json`, `gh api /graphql -F query=@q.graphql`, `gh api /graphql --input -`;

and refuses `gh api -X PUT repos/o/r/pulls/5/merge` and `gh api graphql -F query=@q.graphql`. The supervisor reproduced both in process before the ruling (run/supervisor/probe_083_r4_api.py, no gh run).

On gh 2.97.0 (`gh api --help`, read locally, no network): `-p/--preview`, `-H/--header`, `-q/--jq`, `-t/--template`, `-X/--method`, `-f/--raw-field`, `-F/--field`, `--input`, `--cache` and `--hostname` take a value; gh's flag parser (pflag) takes the word after such an option as its value whatever it begins with, and a string option keeps its last value, so `-X PUT ... -p -XGET` sends PUT. The endpoint is either a REST path or the word `graphql`; a full URL is taken as given, and a REST-shaped POST of `{"query": ...}` to `/graphql` or its URL reaches the GraphQL endpoint. A field value beginning `@` is read from a file, `@-` from standard input; `--input` reads the whole body from a file or standard input.

gh 2.97.0 matches command names neither by case nor by prefix: `gh PR MERGE --help` answers `unknown command "PR" for "gh"`, and `gh pr mer --help` prints the `pr` group's help, not `merge`'s. Review A's question on TASK-083's round 4 (does `gh PR MERGE`, which the guard passes, merge?) is answered no; nothing to fix there.

The reproduction tests: `tests/test_bug046.py`, above its marker line (the known run on f3fa7b4 is quoted in the brief).

## Hypotheses

1. **The method is read from every word of the command.** Discriminating observation: a method-shaped word in any value position (`-p`, `-H`, `-q`, `-t`) after the real method changes the verdict, while the same word as a positional is irrelevant to gh.
2. **The method is read from the right words, but the last method option is not the one gh honours.** Discriminating observation: `-X PUT ... -X GET` would pass (gh sends GET there, so passing is right) while `-X PUT ... -p -XGET` would be refused.
3. **The file-body refusal is keyed to the endpoint word gh_words returns.** Discriminating observation: the same body refused with `graphql` and passed with `/graphql` or the URL.

## Evidence

- `permission-guard.py` (the `gh api` branch of `_check_word_list`, `if group == "api":`): `for i, a in enumerate(w): if a in ("-X", "--method") ... method = w[i + 1].upper() elif a.startswith("--method=") or (a.startswith("-X") and len(a) > 2): ...` walks every word of the command, value positions included; the last match wins. `-p -XGET` sets GET after PUT. Hypothesis 1 holds by reading and by the reproduction; hypothesis 2 is refuted (the reading does not skip values at all).
- The same branch: `if group == "api" and sub == "graphql":` guards the refusal of `--input`, `@` and `=@` words; `sub` is the endpoint as gh_words reads it, so `/graphql` and the URL skip it. Hypothesis 3 holds.
- Both lines stand at TASK-063's merge (b05fbc8): older than TASK-083 and no regression of it.

## Confirmed cause

Hypotheses 1 and 3: the merge refusal's method is read from every word, where gh reads the method only from its own option, a value-taking option's next word being that option's value; and the refusal of a body the guard cannot read is tied to one spelling of the GraphQL endpoint, where gh reaches GraphQL by several. Class: a defeated safety mechanism (the guard's refusal of a merge outside the gate, through REST or through a GraphQL mutation the guard cannot read), reachable in ordinary use by a command that names the merge in its own words, inside the guard's threat-model row (docs/INVENTORY.md, Decisions).

## The fix the supervisor rules

The lesson of TASK-083 (docs/HARDENING.md, TASK-083, "one reading, not shapes"): name what is accepted rather than extend the shapes. The bridge's own `gh api` calls are reads (the report cycle's alerts, check runs) and none sends a body from a file or names a merge endpoint.

- **F1.** A `gh api` call holding a body the guard cannot read is refused whatever its endpoint: an `--input` option in any form, or a word beginning `@` or holding `=@` (a field read from a file or standard input). The `graphql` condition is dropped. A raw field (`-f`) whose value begins `@` is refused with it: an over-refusal, safe.
- **F2.** A `gh api` call naming a pull request's merge endpoint is refused whatever its method, a read included: a word that, lower-cased, with `%2f` read as `/` and `%2e` as `.`, its path's runs of `/` read as one and its dot segments resolved as a URL's are, holds `/pulls/<one segment>/merge`. The method is then read for nothing and its loop may go. `tests/test_permission_guard.py`'s allowed case `gh api repos/o/r/pulls/12/merge` pins the old rule and moves to the refused list.
- Every other `gh api` refusal (the merge mutations by name, the `&` refusal, the alias refusals) is unchanged; `gh pr merge`'s reading (TASK-083) is unchanged.

Not taken, recorded as leads (outside the guard's merge refusal; GitHub's branch rules decide a direct write to a protected branch): REST `POST repos/<o>/<r>/merges` and `PATCH repos/<o>/<r>/git/refs/heads/<b>`, and the GraphQL mutations `mergeBranch`, `updateRef`, `updateRefs` and `createCommitOnBranch`; `gh.cmd`, `gh.com` and a gh named by path as the command's head.

## The fix as built (three rounds)

F2 as first ruled was the brief's error twice over: round 1 resolved dot segments over the whole word and decoded only `%2f` and `%2e`; round 2 decoded every escape until stable and then cut the word at its first `?` or `#`, where gh cuts only at a literal one. Each round's reviews found another spelling gh sends to the merge endpoint that the guard read apart. Round 3, at the ceiling, replaced the spelling rule with one that names what it accepts: a `gh api` word whose decoded (every `%XX` until stable), lower-cased text holds both `pulls` and `merge` is the merge endpoint, refused whatever its method; one decoding per word feeds this rule and the merge-mutation rule. An ordinary word holding both names is refused with it, an over-refusal, safe (docs/HARDENING.md, BUG-046).
