# BUG-041 — the review guard: a snapshot deleted after it was taken reads as one never taken

Found by the security audit of TASK-043's round 3 (its A1), reproduced there on a temporary repository of the projects' layout, with a control without the delete exiting 1; ISS-026. Review B of TASK-043 graded it none of the five for that increment and called its own bug the right split. Read from `bridge/cursor-bridge/review-guard.py` at origin/main ba497cd and shown by the reproduction tests the supervisor wrote first, in `tests/test_bug041.py`, which fail there for the reason given.

**Symptom.** After the launch, a hook planted, a branch made and `.git/bridge/review-<nnn>.json` deleted: `verify` exits 2 with "no snapshot ... run snapshot before the launch": no GATE-INTEGRITY, no void, nothing restored. `snapshot` on the same tree exits 0 and takes the hook and the ref as its baseline, the next launch verifies and premerges clean, and the next `git commit` runs the hook. Without the delete, `verify` exits 1.

**Confirmed cause.** `load_snapshot` returns `None` for any snapshot file that is not there, and both callers return 2 before `snapshot_rewritten` runs. That function already reads a missing file as a difference (`sha256_file` gives `None`, which differs from the recorded hash), but no path reaches it. The copy `snapshot` wrote outside the checkout (FB-037) is the record that a snapshot was taken, and it goes unread. Every line is the state before BUG-039, which pinned `None` for no snapshot file alone (`handoff/TASK-043-r2.md`, Requirement 1).

**The fix.** Where the snapshot file is gone and its hash copy stands, `load_snapshot` hands back an empty snapshot, as it does for content that is not a JSON object, so `verify` and `premerge` reach their rewritten returns: GATE-INTEGRITY, exit 1, nothing restored, no git command, the launch voided by the round's recorded time. `snapshot_rewritten` names the deletion. No snapshot and no copy stays CANNOT VERIFY, exit 2: a snapshot never taken.

**Reproduction:** `test_bug041_a_deleted_snapshot_is_a_flag_and_voids_the_launch`, `test_bug041_premerge_refuses_a_deleted_snapshot_as_a_flag`.

**Negative cases:** `test_bug041_negative_a_deleted_snapshot_restores_nothing_and_runs_no_git`, `test_bug041_negative_the_voided_launch_stays_voided_under_the_next_snapshot`, `test_bug041_negative_a_launch_before_the_round_is_not_voided`; invariants that hold today too: `test_bug041_negative_a_snapshot_never_taken_stays_a_cannot_verify`, `test_bug041_negative_the_snapshot_and_its_copy_both_gone_stays_a_cannot_verify`, `test_bug041_negative_a_standing_snapshot_is_unchanged`.

**What this does and does not hold.** It holds the deletion a reviewer makes in the checkout. It does not hold an act outside the checkout: the snapshot and its copy both deleted reads as never taken, and a reviewer that runs the guard's own `snapshot` rewrites both, each a deliberate reach past KP-032's "in passing", recorded in `docs/HARDENING.md`. After the flag, the next `snapshot` on the same tree still takes what was left as its baseline, as it does after a rewritten snapshot: the GATE-INTEGRITY line printed is what stops the supervisor, who reads the configuration and the hooks first and opens the flag and an issue, and the launch it flagged stays voided under that snapshot. A hash copy is never cleaned up, so a repository re-created at the same path, or a cleared `.git/bridge`, reads as GATE-INTEGRITY and no longer as CANNOT VERIFY for a name that had a snapshot, until `snapshot` runs again: this fails closed.
