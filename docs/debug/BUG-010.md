# BUG-010 — workflow-check.py's usage error with a standard stream closed

Found by stage B2's review, round 9 (Review B, 2026-10-18). Reproduced by the supervisor the same day, with a probe run against the committed program at origin/main 04aee91.

## Symptom
`python bridge/cursor-bridge/workflow-check.py --bogus`:
- both streams open: exit 2, the usage line and `workflow-check.py: error: unrecognized arguments: --bogus` on standard error, `RESULT: not checked` on standard output (the contract the usage text states);
- standard output closed (the child started with file descriptor 1 closed, so Python sets `sys.stdout` to `None`): exit 1 and a traceback ending `AttributeError: 'NoneType' object has no attribute 'flush'`;
- standard error closed (`sys.stderr` is `None`): exit 1, no `RESULT: not checked`, and the usage line lands on standard output.

With a root instead of a bad argument (exit 0, 1 or 2 by the findings), both closed-stream launches end as they do with open streams (test_r014_closed_standard_output_gives_no_traceback covers standard output for those).

## Hypotheses
1. `CheckArgumentParser.error` (workflow-check.py:752-758) calls `sys.stderr.write` and `sys.stdout.flush()` without allowing either stream to be `None`. Discriminating observation: the traceback names `flush` on `NoneType` when standard output is closed. With standard error closed, the usage line still appears, because argparse's own `print_usage` tolerates a missing stream and falls back to standard output. But `RESULT: not checked` does not appear, so the exception rose at `sys.stderr.write`, before the `print`.
2. The entry point's reconfiguration (workflow-check.py:832-834) leaves a closed stream half-configured, so a later write fails. Discriminating observation: the failure would also appear on the root paths, which reach `print` and `sys.exit` through the same streams. It does not: those paths exit 0, 1 and 2 correctly with a stream closed.

## Evidence
Hypothesis 1 holds. The traceback names `flush`. The stderr-closed run prints the usage line and no RESULT line. The root runs with the same streams closed are correct, which rules out hypothesis 2. `print()` to a `None` standard output does nothing in Python, so the only failing calls are the explicit `sys.stderr.write(...)` and `sys.stdout.flush()`.

## Confirmed cause
`CheckArgumentParser.error` writes to standard error and flushes standard output directly, and either can be `None` when the program is launched without that handle. The resulting AttributeError ends the run with exit 1 (and, where standard error is open, a traceback) instead of the usage error's exit 2.

`None` is the closed-stream state itself, not a wrong value standing in for a right one, so a guard that skips the write or the flush on a `None` stream repairs the cause; it hides nothing.

## Reproduction
