# BUG-043 — the loop's claim that builder-written code never runs with the owner's environment

Found by stage T2's review, round 2 (Review A's bridge part, its B1, a REJECT, graded security; Review B silent), confirmed by reading `bridge/cursor-bridge/workflow/phases/delegation-loop.md` at origin/main 603b2d4. It is a defect of text, its own cause; the seven tests of `tests/test_bug043.py` written first fail on that commit for the reason given.

**Symptom.** Step 4 said "code the builder wrote never runs in the loop with the owner's login or secret-like variables (D-004, R-052)", `docs/DESIGN.md` said the same and D-004's note said a run without the flag is instructed only for a driver under a recorded Decision. Six lines on, step 4 let a run of the increment's own test files run in the foreground, the supervisor's or `test-runner`'s, and `bridge/agents/test-runner.md` repeated it. That run is direct, with no launcher and no `--strip`: an execution of the builder's tests, on every increment, on an ordinary layout, before any reviewer has read them, with the owner's `USERPROFILE`, `gh` login and secret-like variables. `tests/test_release_t_strip.py` skips in exactly that case, so no test saw it, and D-004 drew no such edge, so an auditor reading every crossing was told the crossing did not exist.

**Confirmed cause.** R-052's words are "the loop's suite launches", and a suite is defined as more than the increment's own test files. TASK-041 wrote the general claim over that narrower change. The exposure predates the stage; the claim is the stage's.

**The class.** Security, not a regression: untrusted input, files a builder writes, reaches it on every increment (INVENTORY's by-class row: a security finding is judged by whether untrusted input can reach it). REVIEWERS DISAGREE, Review B silent; correctness, not intent; decided for the fix, a false claim of a security property being the one thing the release says it closes.

**The fix.** Close what can be closed and state the rest as a class:
- the increment's own test files go through the launcher, `--strip`, as the supervisor's launch in the background, and `test-runner` reads the file: a foreground launch with the slot held is moved to the background by the app, stays queued with no pid and no log row, and no program can stop it (Review A's B2 of the first text);
- a stripped run that fails for want of a variable takes `--key-file` and is never run again without `--strip`; a 125 naming an option or the agent home is a defect to fix (the audit's A5);
- the claim now says what the launches do: no launch of the loop but a driver under a recorded Decision hands code the builder wrote the owner's login or secret-like variables, and the strip is instructed, no program holding the flag (Review A's S1, the audit's A3);
- whatever does not go through the launcher runs in a session's own environment, stated limits, among them: a runner the launcher refuses, a benchmark or profile, a build, a type check or a linter, a hook a commit runs, a reviewer's or auditor's own run, a root-cause reproduction, an installer rehearsal, a live smoke and a stage demonstration's start of the product. The first text's count of three was a new absolute with the old claim's fault, disproved by its next sentence (Review A's B1 and the audit's B1, convergent, security); a class with "among them" cannot be disproved by the next example. The owner is told (rule 58);
- step 4 reads `.git/config` as a file before the first git command after a builder run (the audit's B2: a `core.fsmonitor` line runs on the next `git status`, probed), the launcher's own check a program item.
