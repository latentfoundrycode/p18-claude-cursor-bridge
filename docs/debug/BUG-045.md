# BUG-045: a -h or --help word anywhere among git's words exempts every git refusal of the permission guard (R-082)

Found 2026-11-16 by Review A of TASK-063's records pull request (#172, closed unmerged), after TASK-063 merged as b05fbc8 (PR #171). Review B had rejected TASK-063's round 3 on one operator of the same defect (`git worktree remove -- --help`); the supervisor judged that operator a contrived layout and recorded it, where decide.md judges the class ("the class is the defect, not the operator that exposed it"). Review A named an operator in ordinary use, and the supervisor reproduced it.

## Reproduction

On main at b05fbc8, from a folder that is no bridge Workspace, `bridge/cursor-bridge/permission-guard.py`'s `check(command, cwd, "Bash")` returns None (passes) for each of:

- `git commit --no-verify -a -m -h`, `git commit --no-verify -a -m --help`, `git commit -n -a -m -h`, `git commit --no-verify -m x -- -h`
- `git -c core.hooksPath=/dev/null commit -m -h`
- `git push --force -o -h origin main`, `git push --force -- --help`
- `git worktree remove -- --help`, `git worktree remove -- -h`

and refuses the same commands without the help word (`git commit --no-verify (...)`, `git commit -n (...)`, `git -c core.hooksPath=... (...)`, `git push with --force`, `git worktree remove (...)`).

On git itself, in a scratch repository whose pre-commit hook exits 1: `git commit -a -m x` exits 1 (the hook refused); `git commit -a --no-verify -m -h` exits 0 and makes a commit whose subject is `-h`; `--no-verify -m --help` the same, subject `--help`. git's option parser takes the word after `-m` as its value whatever its leading dash.

The reproduction tests: `tests/test_bug045.py`, above its marker line. On b05fbc8: `9 failed, 7 passed` (run/agent/BUG-045-known.out in the supervisor's checkout): the nine forms above pass the guard (each failure `(command, 0, '')`), and the six lone help calls and the premise test on git pass.

## Hypotheses

1. **The help exemption is computed from the presence of a help word anywhere among the words.** Discriminating observation: the same refused command with the help word as an option's value, after `--`, and as the lone word after the subcommand all pass alike; a word that only contains `-h` (`-hx`) does not exempt.
2. **The exemption is computed from the word's position, but the git subcommand reader (`git_subcommand`) mislocates the subcommand when a value-taking option precedes the help word.** Discriminating observation: `git commit --no-verify -a -m -h` would pass while `git commit --no-verify -a -h -m x` (help word not in a value position) would behave differently.
3. **The hook-skipper reader (`hook_skipper_option`) misses `--no-verify` when the message is a dash word.** Discriminating observation: `git commit --no-verify -a -m -x` (a dash word that is no help word) would also pass.

## Evidence

- `bridge/cursor-bridge/permission-guard.py:2316`: `helpful = "--help" in w[1:] or "-h" in w[1:]`, a membership test over every word after `git`; `not helpful` gates the hooksPath refusal (2323), `git config core.hooksPath` (2325), the hook-skipper refusal (2330), the force-push refusal (2338) and `git worktree remove` (2344). Hypothesis 1 holds by reading.
- `git commit --no-verify -a -h -m x` passes as well (the help word in an option position exempts in the same way), so the position plays no part: hypothesis 2 is refuted.
- `git commit --no-verify -a -m -x` is refused (`git commit --no-verify (...)`): the hook-skipper reader reads a dash message; hypothesis 3 is refuted.
- The same membership test stands at fae0860:471 and on round 8's guard: the defect is older than TASK-063 and no regression of it.

## Confirmed cause

Hypothesis 1: the exemption tests whether a help word is present anywhere among git's words, where git reads a help word as its help option (printing its help and doing nothing else) only when it is an option of its own; as an option's value or after `--` it is an argument, and git does what the rest of the command says. Class: a defeated safety mechanism (the hook-skipper, hooksPath, force-push and worktree-removal refusals), reachable in ordinary use by a command that names the refused action in its own words, inside the guard's threat-model row (docs/INVENTORY.md, Decisions).

## The fix the supervisor rules (minimum)

The exemption holds only where git cannot be doing anything but printing help: the words after git's subcommand are exactly one help word (`-h` or `--help`), or, for `worktree`, `remove` followed by exactly one help word. Every other command is read as it is today. A help word beside other arguments (`git push --force --help`) is then refused: an over-refusal, safe, and git's help is still reachable as `git help push` or the lone form.

## Round 1's findings (2026-11-16): the same subsystem a second time

The audit ran git: in a scratch repository whose pre-commit hook exits 1, `git --attr-source HEAD commit -a --no-verify -m second` exits 0 and commits, and `git --attr-source HEAD worktree remove <wt>` removes the worktree.
2. **An alias defined in the command for a hook-skipping subcommand passes.** `_alias_names_refused` refuses an alias whose value names `worktree remove`, `pr merge` or a forced push, and none for the other hook skippers: `git -c "alias.cm=commit --no-verify -am" cm x` passes under both tools; and with the help exemption, `git -c core.hooksPath=nohooks -c "alias.cm=commit -am" cm -h` passes and git commits with subject `-h`, the hooks off (Review A, on git 2.53).

Both are a defeated safety mechanism, inside the threat-model row (a refused action named in the command's own words, behind an option or an assignment the guard reads), neither a regression of round 1. A second round on the same reader, so the design changes rather than the list growing (the supervisor's working rule for the tail): **the global options before the subcommand are read from a known list and any other one is refused as unreadable**, so a new git option cannot reopen it; and **an alias defined in the command whose value names a hook-skipping subcommand is refused**, as the aliases for the other refused actions are. ## Round 2's findings (2026-11-16): each family a second time

Round 2's builder made the ruled change (the supervisor's run of the guard's test files: `1523 passed, 20 skipped`; git 2.53 rejects the glued `-Csub` and `-ccolor.ui=never` with exit 129, so their refusal is harmless; the Bash and PowerShell readings agree). Its known option lists hold against git 2.53 (the security audit checked every entry, and that git accepts no abbreviation of a global option). Five gaps remain, none a regression of round 2, each a defeated safety mechanism inside the threat-model row:

1. **An alias value is read by its first raw word, where git splits it as a shell does.** The supervisor: git honours a global option at the start of an alias value, so `git -c "alias.cm=-c core.hooksPath=/dev/null commit" cm -a -m x` commits with the hooks off (a scratch repository whose pre-commit hook exits 1), and round 2 passes it. Review A: a quoted value (`alias.cm='commit' -n -am`, `alias.cm="commit"`, `alias.cm=c"ommit"`) passes round 2, and git runs `commit` for each (git 2.53: `git -c "alias.v='version'" v` prints the version).
2. **A dotted alias key escapes every alias refusal.** `_alias_key_char` reads letters, digits, `_` and `-`, so `alias.v.x=...` stops the key reader before `=`: `git -c alias.v.x=commit v.x -am x` and `git -c 'alias.v.x=!echo hi' v.x` pass (git runs the shell alias: it printed its text). The `!` half is older than BUG-045.
3. **An abbreviated `--no-verify` passes.** `hook_skipper_option` matches the word exactly; git accepts any unambiguous prefix of a long option: `git commit -a --no-verif -m x` and `--no-veri` commit with the pre-commit hook skipped, and `git push --no-verif origin HEAD:refs/heads/main` pushes with the pre-push hook skipped (the security audit, git 2.53).
4. **An abbreviated `--mirror`, `--force-with-lease` or `--force-if-includes` passes.** `force_push_reason` reads prefixes of `--force` only: `git push --mirr origin` rewrote the remote (`(forced update)`), and `--force-w`, `--force-with=main` pass the guard.
5. **`git config` reads a `--get` word as a read even where it is an option's value.** `git config --comment --get core.hooksPath /dev/null` passes, and git sets `core.hooksPath` to `/dev/null`; a later commit skips its hook. And a relative value passes by design: `git config core.hooksPath nohooks` points the hooks at a folder that holds none.

Each family has now been met twice, so each reading is made whole rather than extended: **every alias defined in the command is refused, whatever its key or value** (a word of git's that begins `alias.`, in any case, and holds `=`): the guard does not expand aliases, and the loop defines none; **a refused long option is read by any prefix git accepts as its abbreviation** (`--no-verify` on the hook skippers; `--force`, `--force-with-lease`, `--force-if-includes` and `--mirror` on push), an `=value` suffix apart; and **a `git config` command that names `core.hooksPath` passes only in its read forms** (`git config core.hooksPath`, `git config --get core.hooksPath`, `git config get core.hooksPath`) **and in the one write the bridge instructs**, `git config core.hooksPath .githooks` (configuration.md, the configurator, the configuration policy; `tests/test_allowlist.py` holds it), every other one refused: a relative value no longer passes by design, only the bridge's own hooks folder. Every alias refused on its word alone also changes what one earlier acceptance case sees: `test_r082_a_long_word_is_refused_for_its_removal_within_the_hooks_time[alias-value-with-a-long-run-of-blanks]` (the supervisor's file) may now be refused for its alias before its removal; the supervisor amends it to accept either refusal within the hook's time. The reproduction: `tests/test_bug045.py`, the section "round 2's findings", above the marker; round 2's `alias-for-status` case moves there, refused.

Leads, outside the threat-model row (the refused setting is not in the command's own words): `git -c include.path=<file>` reads a file written earlier that may set `core.hooksPath` (Review A); `git config alias.<x> "<value>"` writes an alias into configuration that a later command runs (the brief packager). `--shallow-file`, a value-taking global option git reads, is refused as unreadable: an over-refusal.
