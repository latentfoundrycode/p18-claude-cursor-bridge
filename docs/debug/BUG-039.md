# BUG-039 — the review guard's four sites: a flagged round was spent, and one git call kept the file monitor on

Found by release T's diagram retrofit (D-003, D-004), its critique's rounds 2 and 3, and Review B of PR #116. R-042 says a flagged round spends nothing, whichever of `verify`'s checks flagged it and whenever; D-003 draws that and D-004 draws every git command of the guard with the hooks and the file monitor off. Each cause below is read from `bridge/cursor-bridge/review-guard.py` at origin/main 67e79b9 and shown by a reproduction test the supervisor wrote first, in `tests/test_bug039.py`, which fails there for the reason given (run 2026-11-02 on task-043 before the brief). Every site is its own cause, proven by the code and the test, so no instrumentation round ran and one fix brief names them all.

**Fixed points of the fix.** `tests/test_bug039.py` calls these names, so the fix keeps them: `record_flagged_launch` (the function that records the void); `flagged_launch` (the round entry's key, holding the voided launch's start time as `launch_info` reads it); `_git_proc` (the helper, the one call site of git in the program).

## 1. Four early GATE-INTEGRITY returns never void the launch
- **Symptom:** a Review B run exits 0, `verify` flags GATE-INTEGRITY at one of its early checks, and the next snapshot of that round on a changed tree is refused `round N is reviewed`: the flagged round is spent.
- **Confirmed cause:** `cmd_verify` returns 1 at four places without calling `record_flagged_launch`: the snapshot rewritten (`snapshot_rewritten`), `.git/config` or a hook changed (`if flags:` before any git command), the branch held in another worktree (`held_elsewhere`), the branch not put back (`now_on != snap["branch"]`). Only the flags at the end of the function call it. `err_counts_as_reply` then counts the exit 0 at the next snapshot.
- **Reproduction:** `test_bug039_site1_a_flag_before_any_git_command_voids_the_launch` (three cases), `test_bug039_site1_the_branch_held_in_another_worktree_voids_the_launch`, `test_bug039_site1_the_branch_not_put_back_voids_the_launch`: no `flagged_launch` today.
- **Negative cases:** `test_bug039_site1_negative_no_path_clears_a_recorded_flag`; `test_bug039_site1_negative_a_snapshot_rewritten_to_any_shape_stays_a_clean_flag`, `test_bug039_site1_negative_a_rewritten_snapshot_voids_no_launch_before_the_round`, `test_bug039_site1_negative_the_void_runs_no_git_on_the_pre_git_returns`.
- **Round 1's correction (Review A's Blocking 1 and the security audit's B1, convergent):** round 1's void at the first return read `taken` from the snapshot it had just found rewritten. A rewrite to a future `taken` or to `zzz` voided nothing, so the next snapshot on a changed tree was refused as reviewed, and with the bytes put back the next `verify` wrote a mark; a rewrite to `{}` voided a launch from before the round. And `load_snapshot` raises on text that is not JSON and returns `None` for `null`, so those rewrites never reached the return. The fix: at that return the void reads nothing of the snapshot and compares with the round entry's `time`, from the hash-checked record; `load_snapshot` gives an empty dict for any content that is not a JSON object. Handed to the builder in `handoff/TASK-043-r2.md`.

## 2. A flag raised while the run still goes on leaves its launch unvoided, and a later clean verify admits it
- **Symptom:** `verify` during the run flags GATE-INTEGRITY and repairs what it found; the run then exits 0; the launch counts as the round's reply. A second `verify` finds nothing left to flag, so it writes `reply` 0 and a verified mark `premerge` accepts: a flagged review reaches the merge.
- **Confirmed cause, two lines:** `record_flagged_launch` returns on `exit_code != 0`, and an `.err` with no exit line reads `None`, so nothing is recorded while the run goes on. And the end of `cmd_verify` writes `reply` 0 and the mark for any launch with exit 0 at or after the snapshot, without reading `flagged_launch`, so even a recorded void does not stop a clean `verify` (reading the same function; the plan's negative case, "a flagged round's launch is admitted by no path", is what it breaks).
- **The fix's two parts:** `record_flagged_launch` records the void by the launch's start time whatever the exit so far, where the `.err` holds a started line at or after the snapshot; and a `verify` whose launch start equals the round's `flagged_launch` still restores the tree, as it does today, but writes no reply and no mark, prints a GATE-INTEGRITY line saying the launch was voided and Review B runs again, and exits 1. A new launch has a start time of its own and is admitted.
- **Reproduction:** `test_bug039_site2_a_flag_during_the_run_voids_the_launch_that_later_exits_0`.
- **Negative cases:** `test_bug039_site2_negative_no_path_admits_a_flagged_launch`, `test_bug039_site2_the_void_holds_whatever_the_exit` (three cases), `test_bug039_site2_negative_a_voided_launch_stays_voided_under_a_later_snapshot`, `test_bug039_site2_negative_a_voided_verify_still_restores_the_tree`, `test_bug039_site2_negative_a_launch_before_the_snapshot_is_not_voided`, `test_bug039_site2_negative_a_void_touches_only_its_key`.
- **Round 1's correction (Review A's Should fix 3 and the security audit's B2, convergent):** the check at the end of `cmd_verify` read the record only `if os.path.isfile(rpath)` and acted only `if not err`, so a record deleted or changed outside the guard, its hash copy standing, skipped the check and wrote the mark, and `premerge` accepted it. The first brief had ordered today's handling here; the plan's negative case, "admitted by no path", is what the reproduction breaks. The fix: the record is read once with no `isfile` guard, and a tamper report is GATE-INTEGRITY, exit 1, no mark. A record and its copy both missing stays no error. Test: `test_bug039_site2_negative_a_tampered_record_admits_no_launch` (two cases).

## 3. `premerge`'s git call bypasses the helper
- **Symptom:** the one git command of the guard run without `core.fsmonitor=false`, against the guard's docstring and KP-032.
- **Confirmed cause:** `cmd_premerge` calls `subprocess.run(["git", "-c", "core.hooksPath=" + ..., "merge-base", "--is-ancestor", ...])` directly, not `_git_proc`. Its consequence is small: the command reads no worktree, and `verify` has already flagged a changed `.git/config`. The caller reads its return code, so the fix uses `_git_proc`, not `run_git`, which raises on a non-zero exit.
- **Reproduction:** `test_bug039_site3_every_git_command_of_premerge_runs_with_both_switches`, `test_bug039_site3_no_git_call_of_the_guard_bypasses_the_helper`.
- **Negative case:** `test_bug039_site3_negative_premerge_runs_no_planted_hook_or_monitor`, an invariant that holds today too, since `merge-base` reads no index and so never starts the monitor (the plan expected it red; the run shows otherwise). It is shown strong by a mutant of the fixed guard that takes the switches out of `_git_proc`, where `status --porcelain` starts the planted monitor. Review A of round 1 found its hook half had no precondition, since `premerge` wrote no index whether the hooks were on or off; a changed time on a tracked file now makes `status` rewrite the index, the event the hook is planted on.

## 4. A re-snapshot drops the flag
- **Symptom:** a flagged round taken again on the same tree counts the flagged launch's exit 0 as its reply, so its next snapshot on a changed tree is refused as reviewed.
- **Confirmed cause:** `cmd_snapshot` rebuilds the round's entry keeping `reply`, `lift`, `lift_line` and `time`, and not `flagged_launch`. Found by Review B of PR #116, which reproduced it on a temporary repository.
- **Reproduction:** `test_bug039_site4_a_resnapshot_keeps_the_flag`.
- **Negative case:** `test_bug039_site4_negative_a_resnapshot_counts_no_reply_on_either_tree` (same tree, changed tree).

## 5. Flags already found are lost when a later git step fails
- **Symptom:** a reviewer's new branch and a file `git clean` cannot remove, a process left holding it: the refs are repaired, `clean` fails, `verify` exits 2 with CANNOT VERIFY and never prints GATE-INTEGRITY; no void is recorded, and once the file is released the next `verify` finds nothing left and writes a mark. The supervisor never learns of the flag.
- **Confirmed cause:** `cmd_verify` collects `flags` in its step 2 and prints them only after its step 4; `run_git` raises between them, and `main` catches it. Found by the security audit of round 1 (B3), reproduced on a temporary repository. The state before this bug's fix; R-042's "whichever of `verify`'s checks flagged it and whenever" covers it.
- **Reproduction:** `test_bug039_site5_a_git_failure_after_a_flag_keeps_the_flag`.
- **Negative case:** `test_bug039_site5_negative_a_git_failure_with_no_flag_voids_nothing`, an invariant.

## 6. The guard's "empty" hooks folder lies where the reviewer's run writes
- **Symptom:** hooks planted in `.git/bridge/no-hooks/` ran under `verify`, which printed OK, and under `premerge`'s `git status`, inheriting the owner's environment.
- **Confirmed cause:** `no_hooks_dir` returns a fixed path inside `.git/`, and nothing hashes it or checks that it is empty, the hole KP-032's second pass closed for `.githooks`. Found by the security audit of round 1 (B4), reproduced on a temporary repository; the state before this bug's fix. The fix: a folder outside the repository, made fresh per process.
- **Reproduction:** `test_bug039_site6_a_hook_planted_in_the_guard_s_folder_never_runs` (two cases), `test_bug039_site6_the_hooks_folder_lies_outside_the_repository`.

## 7. An exit line past `int()`'s limit raises
- **Symptom:** an `.err` holding a 5,000-digit exit line at a flag's return: the GATE-INTEGRITY line, then a traceback, and no void.
- **Confirmed cause:** `launch_info` runs `int()` on an unbounded run of digits, and `main` does not catch `ValueError`. The crash is the state before this bug's fix; round 1's calls make it reachable at the four early returns. Found by the security audit of round 1 (A3).
- **Reproduction:** `test_bug039_site7_an_exit_line_too_long_to_read_is_no_exit`.
