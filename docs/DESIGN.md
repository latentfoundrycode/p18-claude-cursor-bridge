### The weekly dependency scan

The floor's OSV-Scanner runs only on a pull request's or a push's event, over the whole lockfile as it stands then, so a flaw disclosed later in an unchanged dependency, or in a paused or finished project with no event, was never flagged (the owner, 2026-10-28). The design: a second workflow file, `.github/workflows/dependency-scan.yml`, run on a weekly `schedule` (Sunday 06:17 UTC — off the hour, since GitHub delays the `schedule` event at high-load times, "the start of every hour" among them — which precedes the Sunday evaluation's 14:00 on the owner's clock, UTC+1 or UTC+2, `evaluate-reports.md`; a run still queued or running at the evaluation's hour is not read this Sunday — where nothing else completed since the previous evaluation, that is the third kind below, with no rerun — and is read the next, unless a newer run has completed, whose time passes it and leaves it unread) and on `workflow_dispatch`; `permissions: contents: read` and nothing else; a checkout without persisted credentials; OSV-Scanner at the floor's version and SHA-256 — one pin stated twice, so the workflow's structural test asserts the two equal and T9's deprecation check names both — run over every lockfile the repository holds (`osv-scanner scan source --config=osv-scanner.toml --lockfile=...` per lockfile, as the floor's step does) with the floor's exit-code handling (0 clean; 128, no lockfile read, fails as KP-005 says; every other code fails as it is) and one line more than the floor's, `dependency-scan: OSV-Scanner exit <code>` printed on every non-zero exit, which the evaluation reads; no token and no secret anywhere in it: no `secrets.` reference and no token handed to a step (the automatic `GITHUB_TOKEN` exists in every job, here with `contents: read` alone, used only by the checkout's own fetch and removed before the next step, the checkout persisting no credentials), which is what the structural test's "no secret" asserts. **What the Sunday evaluation reads** (`bridge/commands/evaluate-reports.md`, a step the maintainer's command gains, R-052): each project's workflow state and its runs since the previous evaluation — first `gh workflow list --all`, where any disabled state (`disabled_inactivity`, or `disabled_manually`, hidden the same way and started by no `gh workflow run`) is the third kind below whatever the runs show, since `gh run list --workflow dependency-scan.yml` lists no run of a disabled workflow without `-a` (gh's own reference, read 2026-11-01 on gh 2.97.0: `gh workflow list` "hiding disabled workflows by default", and both commands' `-a, --all  Include disabled workflows`) and an old success would otherwise read green; then `gh run list --workflow dependency-scan.yml --created ">=<the previous evaluation's date>"`, the date the ledger (`Reports/ledger.json`) keeps as its `_meta.last_extract` stamp for the previous run, read before this run's extract overwrites it (a nothing-new week leaves no run folder, so the folder is not the record), listed with `--json databaseId,createdAt,status,conclusion`, the window being the listed runs whose `createdAt` is later than the `last run read:` time the previous evaluation's Dependency scan section gives for the project, the creation time of the newest completed run that evaluation read, or the previous section's value where its window completed none, `none` where there was no previous one (a section reading `none` leaves every listed run in the window, and where no previous section names the project the window is the listed runs created on a later day than that date, so a run of that day cannot cover this Sunday: Review A and Review B, TASK-041, round 2): the date is a day and the schedule runs on the morning of the evaluation's own Sunday, so the date alone would take in the run already read and hide a late or missing schedule behind it; a creation time, not the run's id, since GitHub documents no order of its ids; a run re-run from the Actions tab keeps its creation time and is not read again, the rerun the evaluation names (`gh workflow run`) starting a new run; and the section carries `finding standing: run <id>` from week to week until a later run ends `success`, so a finding the narrower window would drop is reported every week it stands (Review A and Review B, TASK-041); a project whose workflow list holds no `dependency-scan` is `not configured`, its calibration's item, or the reason its inventory records where the file waits for the bridge release that carries a newer floor pin, with `last run read: none`, and a project with no GitHub remote is written `no remote`, with its recorded reason (BUG-042); the window gives each run its status and conclusion, and for a `failure` `gh run view <run id> --log-failed` gives the step's `dependency-scan: OSV-Scanner exit <code>` line, which tells the first two kinds apart — in **three kinds, defined here once** (R-052, Failure modes and the inventory's row say the same): (1) **a finding**: a completed run of the window whose conclusion is `failure` and whose exit line reads `exit 1` — a flaw, fixed by a `DEP-<nnn>` increment, the merge policy's procedure, never by an unreviewed change; a finding stands until a later run ends `success`, in that window or a later one, a later run of the second kind superseding nothing, both then reported; (2) **a scanner failure**: the window's last completed run proved nothing — a `failure` with any other exit code (127, 128 or another) or with no exit line at all (the step never reached the scanner: the checkout or the download failed), or any conclusion other than `success` and `failure` (`cancelled`, `timed_out`, `startup_failure`, `skipped`, `action_required`, `neutral`, `stale`) — reported as such with the rerun's one command, `gh workflow run dependency-scan.yml`, the rerun read at the next evaluation; (3) **no completed run since the previous evaluation**: the workflow disabled, no run of the window listed, a list the login cannot read, or only runs still queued or in progress at the reading (a late schedule) — a finding of its own, never green (KP-005: silence is not green), reported with its remedy: the enabling run sheet below where the workflow is disabled, the rerun command where no run is listed, and none where a run is in progress, which the next Sunday reads. A window whose last completed run ended `success` with no finding standing is green. The host fact that makes the third kind certain, read from GitHub's documentation on 2026-11-01 ("Disabling and enabling a workflow"): *in a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days*; a schedule may also start late. So every paused or finished public project reaches the third kind within two months, the evaluation names it, and the remedy is a run sheet for that project's owner — `gh workflow enable dependency-scan.yml`, then `gh workflow run dependency-scan.yml` (or the Actions tab's *Enable workflow*) — the enabled run read at the next evaluation; the documentation names public repositories, and a private one is read the same way, its missing run the same finding. Two more of GitHub's facts, read from the same documentation ("Events that trigger workflows"): *this event will only trigger a workflow run if the workflow file exists on the default branch* (`workflow_dispatch`), and *scheduled workflows will only run on the default branch*; so the workflow's first proof, one `workflow_dispatch` run read green, comes after the file reaches the default branch — after the configuration increment's merge for a project, after this repository's increment merges here — read by the supervisor then and by the evaluation at the latest, never a Done criterion before the merge. Dependabot alerts: the owner switched them on (2026-11-01, "Yes, I switched Dependabot on"); whether GitHub's separate option that enables them for new repositories was taken is not verified, so the evaluation reads each project in two calls that tell the three results apart: `gh api repos/<owner>/<repo>/vulnerability-alerts` answers 204 where the alerts are enabled and 404 where they are not (GitHub's REST documentation, read 2026-11-01; the owner's login has the admin read it needs on their own repositories), a 404 the finding "alerts off"; then, after a 204 only, `gh api --paginate repos/<owner>/<repo>/dependabot/alerts?state=open`, every page, an empty list being alerts on with nothing open; a 403 on either call is the login's scope, named in a run sheet, never a token in text, the project's Security tab the fallback; the bridge writes nothing for them. The convention text (`Cursor-Project-Configuration.md`, the security-floor section) says every project has the workflow; `cursor-configurator` writes it from a frozen block that carries the exit-code handling, with one fill-in, the `--lockfile=` list copied from the floor's OSV-Scanner step in the project's `tests.yml` (OSV-Scanner finds a lockfile by its standard name alone, so this repository's `requirements.lock` needs the floor's `requirements.txt:requirements.lock` form and a recursive scan would miss it), the structural test asserting the frozen part equal to the block and the list equal to the floor's; the increment that adds it to a project is proved by one `workflow_dispatch` run the supervisor reads green after its merge, beside the structural test before it (T9's rule: a floor is trusted only after it ran; the dispatch fact above); `conformance-check.py` gains no floor for the file in this release (a floor for it is a program item for the maintainer's next program release, named in the CHANGELOG entry), BUG-042 only keeping the file from answering for the gate's rows, since it is a second workflow and the floor's steps stand in the gate; the calibration's `Running projects must` item adds the workflow to each running project as configuration.

**The reader.** One reader in `bridge_env.py` (`read_header(text)` → the header as a mapping or `None`, and the body; `check_header(kind, header)` → the schema findings; `HEADER_SCHEMAS`), imported by every program above — `conformance-check.py` and `bridge-install.py` load `bridge_env` by file already and keep doing so. It reads a **stated subset of YAML**, enough for the schemas and no more: `key: value` lines with a scalar — a double-quoted string (with `""` and the two escapes a path or a sentence needs, `\"` and `\\`), a decimal integer, exactly `true`, `false` or `null`, nothing (null), or a **plain** scalar read as a string only where it is a word of letters, digits, `_`, `-` and `.` that starts with a letter and is not, in any case, one of YAML 1.1's typed words (`yes`, `no`, `on`, `off`, `y`, `n`, `true`, `false`, `null`, `~`); every other plain scalar — a date such as `2026-11-04`, a number with a point or a sign, an octal, hex or sexagesimal form, a word with a space or a colon, one of the typed words in another case — is refused with its line and the advice to double-quote it, as is a single-quoted scalar, which the subset does not read, so that a value `pyyaml`'s resolver would type is never read as a string here while another reader reads it as a date or a boolean; or a flow list `[a, b]` of such scalars; block lists (`- ` items, scalars or mappings); nested mappings and block lists by two-space indentation, at most eight levels deep in all (the schemas need six), a deeper block, mapping or list, refused with its line, so that a hook meets the malformed fallback and never a recursion error; `#` comments, a comment starting at a `#` outside a quoted string that opens the line or follows a space, so that `"PR #135"` is text; a byte-order mark tolerated. Only the ASCII space is whitespace to it. It refuses, each at its own line and in a quoted string or a comment too, a tab, any other control character, a lone carriage return, U+0085, U+2028, U+2029, a surrogate, U+FFFE and U+FFFF, the body being left as it stands; and any other non-ASCII character outside a quoted string or a comment. These are a narrowing `pyyaml` does not make in every case, chosen over matching how it reads each one (TASK-046's round 1 showed a comment hiding a key behind U+2028, and control characters it refuses being read), so what the reader accepts it reads as `pyyaml` does, and no header needs them. It refuses an anchor, an alias, a tag, a flow mapping (`{a: b}`, alone or inside a list: the subset writes mappings in block form only), a multi-line or block scalar, a duplicate key and a block above 262,144 bytes, each with its line. The migration quotes every string that the plain form would refuse (every date, every value such as `on`, every path with a space) and the empty string, written `""`, since a blank value reads as null, and the templates show them quoted. It is **not** `pyyaml`: every program is a one-shot script on the owner's interpreter and `bridge_env` is the one module they share (D-002's rule); a third-party import there would be the first in the installed programs and would turn a missing package into a failed hook at every session start. `pyyaml` (6.0.3, in `requirements.lock` for seven tests already) is used **in the tests only**: a test parses every fixture header (TASK-046) and every header of this repository's migrated records (TASK-054, under R-063) with `yaml.safe_load` and asserts the subset reader returns the same value, so a header any YAML reader accepts is read the same here, and every plain form the subset refuses unquoted is one `safe_load` types as other than a string (a date, `on`, a number) or one the schemas never write unquoted (a word with a space, a colon or a slash, which the migration quotes), the test pinning that disjunction and not the first half alone. Alternatives considered: `pyyaml` at run time (rejected above); JSON front matter (rejected: a JSON block is unreadable prose and the plan's words are YAML, which Markdown viewers render as front matter); TOML (rejected: `tomllib` reads it on 3.11 and later only and viewers do not render it).

### Failure modes

A header and its prose disagree: the record's checker fails at the next checkpoint, the program having read the header; the supervisor fixes the one that is wrong. A malformed header: a checker refuses with the line, a hook falls back and says so, the launcher and the guard refuse, the evaluation falls back and names it.
